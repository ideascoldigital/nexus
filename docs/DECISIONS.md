# Nexux — Decisions

ADR-lite log. One entry per decision: context → decision → consequences. Append new ones at the end with a date. If a decision is reversed, do not delete it — mark it `SUPERSEDED by D-XX`.

---

## D-01 — Local-first, no mandatory cloud (2026)

**Context:** the project dropped the multi-tenant/Firebase mode.
**Decision:** everything runs locally: SQLite, LanceDB, Ollama, Docker. Cloud (Civo/AWS, Telegram, GitHub) is optional and incremental.
**Consequences:** no multi-user auth; `NEXUX_MODE=server` exists in config but its adapters throw "not implemented".

## D-02 — Claude manual on the host; automation only for non-Claude brains

**Context:** foundational rule (see `AGENTS.md`, `CLAUDE.md`).
**Decision:** never `claude -p` or any headless Claude CLI **on the host**. Claude is used interactively (`claude code`) with native context via `.claude/` + symlink. Programmatic automation uses Codex/xAI/Ollama.
**Consequences:** `@nexux/llm` has no Claude client. Sanctioned exception: `runClaudeTask` in `@nexux/sandbox` runs `claude -p` **inside the sandbox** (VM/container), launched from the UI — the host stays clean.

## D-03 — pnpm + Turborepo monorepo; packages with no build step

**Context:** a single Next.js app needed to share code with the Tauri app (spec 11-monorepo-migration).
**Decision:** pnpm workspaces + turbo; the 9 packages export `./src` directly (raw TS), consumed by tsx / Next's bundler.
**Consequences:** zero per-package build pipeline; `typecheck` depends on `^build` in turbo; apps are the only composition point.

## D-04 — SQLite + Prisma with a custom migration runner

**Decision:** better-sqlite3 adapter, singleton client, forward-only migrations tracked in `_nexux_migrations`, optional auto-migrate via `NEXUX_MIGRATIONS_DIR` (needed by the Tauri sidecar, which migrates in `~/.nexux`).
**Consequences:** never edit applied migrations; the generated client is committed (`src/generated/`).

## D-05 — Embeddings: Ollama `nomic-embed-text` + LanceDB (no MiniLM, no cloud)

**Context:** spec 12; local semantic search exposed as the default tool for any brain.
**Decision:** default provider = `ollama-nomic` (8192-token context); per-project LanceDB in `<dataDir>/indexes`, three buckets (repo / conversations / project-data), incremental indexing by content-hash (`EmbeddingIndex`).
**Consequences:** requires Ollama running; other providers are declared but stubbed.

## D-06 — Two separate execution surfaces: harness vs sandbox

**Context:** specs 13 and 14.
**Decision:** `@nexux/harness` = ephemeral local Docker, locked down (`--network none`, read-only, cap-drop), for a brain's write→run→observe loop. `@nexux/sandbox` = a full VM (Terraform Civo/AWS) or local DinD, bootstrapped with cloud-init, for real dev/test with Claude Code.
**Consequences:** do not merge them; the harness never gives shell access to the host. Harness warm pool = pending P1.

## D-07 — Tauri v2 with Next.js as a Node sidecar (not a Bun single binary)

**Context:** spec 11-bun-distribution evaluated compiling everything with Bun.
**Decision:** Bun cannot produce a working single binary for Next (SSR/RSC/middleware). We bundle Node + the built Next server as a Tauri sidecar (:3030), DB in `~/.nexux/nexux.db`, process killed on exit.
**Consequences:** the native bundle is larger; native dev uses :3100 with no sidecar.

## D-08 — Telegram via long-polling, no webhook

**Context:** local-first — there is no public URL.
**Decision:** singleton bot with long-polling (survives hot-reload), per-project routing, control by reply, `#task_`/`#sandbox_` tags.
**Consequences:** exactly one process must poll; zero extra infra.

## D-09 — Credentials: env-only towards Terraform; dedicated keypair per installation

**Decision:** cloud credentials reach Terraform via environment variables, never disk; a single ed25519 key (`<dataDir>/ssh`) is offered to sandboxes (`IdentitiesOnly` — agent keys were exhausting MaxAuthTries). Tokens (git, Claude OAuth) live as saved credentials in the DB, selectable per sandbox.
**Consequences:** rotation is simple; VS Code Remote-SSH works via a managed Include block in `~/.ssh/config`.

## D-10 — Roadmap generator: propose/Apply split

**Context:** the definition → features bridge (spec 15, commit `0a37f4d`).
**Decision:** `POST /roadmap/generate` only proposes (zod + retry + filtering of hallucinated keys); nothing is persisted without `POST /roadmap/apply` (single transaction). UI with a reviewable tree.
**Consequences:** a pattern to repeat for any AI generation that writes to the DB: propose → review → apply.

## D-11 — React Query + fetch services; no global store

**Decision:** TanStack Query (staleTime 5s) over a thin `services/*` layer → `/api`; Prisma types end-to-end from `@nexux/db`. No Redux/Zustand.
**Consequences:** shared query invalidation is the sync mechanism between views (e.g. Settings ↔ sandbox drawer).

## D-12 — Bootstrap projects: scaffold at creation, not a separate wizard (2026-07-19)

**Context:** starting an idea from scratch required creating the folder/repo by hand and then going through the wizard as if they were existing repos.
**Decision:** `POST /api/projects` accepts `bootstrap: { type, parentPath }` and does everything in the same request: scaffold on disk (`<parentPath>/<slug>`, README + docs/IDEA.md + per-template extras, `git init` + initial commit with explicit paths), a project with `Project.bootstrapType`, main repo `cloneStatus: ready`, and **pre-seeding of StackNodes/Edges** according to the template (e.g. fullstack → postgres + redis wired to the repo). Templates live in `apps/web/src/lib/bootstrap/templates.ts` (client-safe, reuses `SERVICE_CATALOG`); the scaffolder in `scaffold.ts` (server-only). The wizard stays the same (project → definition → stack → orchestrate); the Stack step simply opens already wired.
**Consequences:** a single creation flow for all three paths (scan/manual/bootstrap); a git failure is a non-fatal warning (`bootstrapWarnings`); a non-empty existing directory → 409, never overwritten.

## D-13 — Global credentials, not per-workspace (2026-07-20)

**Context:** `CloudCredential` filtered strictly by workspace (no fallback), unlike Settings (`ws:<id>:` prefix with a global fallback). Real-world result: the GitHub token saved in the default workspace was invisible to projects in other workspaces — a sandbox with no `GITHUB_TOKEN`, and the env vars panel did not show it.
**Decision:** credentials are **global**: every read (`GET /credentials`, setup wizard, `resolveGitCredential`, `resolveClaudeCodeToken`, overview readiness, skills registry) stops filtering by workspace. The `workspaceId` column is kept only as provenance (who saved it) — no migration. The setup GET now also exposes credential tokens as rows in the Environment variables panel (`source: "credential"` + name, masked), so nothing reaching the sandbox env is invisible.
**Consequences:** a single credential pool for all workspaces (local-first install, single user); if real scoping is ever needed, the column is still there. Settings keep their per-workspace override mechanism with fallback.

## D-14 — Local sandboxes mount folders without a remote (2026-07-20)

**Context:** launching a sandbox required a `repoUrl` on some repo. A freshly bootstrapped project only has a local folder with `git init` (no remote) → blocked with "No repositories with a clone URL".
**Decision:** in **local** (Docker) sandboxes, repos with no URL but with a `localPath` are **bind-mounted** into the container at `/opt/nexux/<slug>` (devcontainer style): `SandboxRepoSpec.mountPath`, `-v` on `docker run`, and the bootstrap skips the clone but keeps `.env` + install/build. A git token is only required if there is something to clone. Cloud (Civo/AWS) still requires a URL — the local folder is not reachable from the VM; the error now suggests using a local sandbox.
**Consequences:** the agent's changes land directly in the real folder (no PR); ideal for bootstrap ideas. Sandbox isolation no longer covers the mounted folder — an explicit choice of local-without-remote mode. `createPr` cannot work without a remote (runner WARN).

## D-15 — Dev console attachments: host staging + scp/docker cp (2026-07-20)

**Context:** sending images/documents with a dev console prompt requires getting binaries into the sandbox. The existing mechanism for context files (`materializeContext`) embeds base64 in the shell command — fine for small markdown, but it breaks with multi-MB binaries (argv length limit, MAX_ARG_STRLEN).
**Decision:** files are **staged on the host** (`<dataDir>/dev-attachments/<uuid>/`, metadata in `SandboxTask.attachments`) BEFORE creating the task (the worker may pick it up instantly), and the runner pushes them with `pushLocalDir` (mirror of `fetchRemoteDir`: local `docker cp` / cloud `scp -r`) to `/opt/nexux/.attachments/<taskId>/`, chowned to the agent user. The prompt lists the remote paths in an `# Attachments` section and Claude reads them with its Read tool (multimodal for images). The dev route POST accepts JSON (prompt only) or multipart (prompt + files, max 10 / 25 MB). The UI shows chips (name/mime/size) — host paths never reach the client.
**Consequences:** any file type works with no shell limits; if the push fails, the run continues with a WARN and the prompt does not mention files that never arrived.

## D-16 — Per-project MCP servers for the sandbox's Claude (2026-07-21)

**Context:** there was no native way to give MCPs to the sandbox's `claude`; the only path was the setup script with `claude mcp add`.
**Decision:** `SandboxConfig.mcpServers` (Json, Claude Code's native `mcpServers` shape) editable as JSON in the wizard's Tooling step. The bootstrap writes it to `~/.claude.json` for both users (agent + root) alongside `hasCompletedOnboarding` — **user scope**, because per-project `.mcp.json` files require interactive approval that a headless run cannot give. It applies to the dev console, headless tasks and the in-app terminal; servers inherit the sandbox env (secrets go as project env vars, not inline). Validation in the wizard's `save()` (JSON of objects) and zod on the PUT; `Prisma.DbNull` to clear.
**Consequences:** changes apply to sandboxes launched after saving (bootstrap-time config); `.claude.json` with onboarding is now written whenever Claude Code is installed (previously only with a token).

## D-17 — GitLab support in the tasks pipeline (2026-07-21)

**Context:** the PR pipeline was GitHub-only (`gh pr create`, assets branch via GitHub's contents API), even though GitLab cloning and credentials already existed (`GITLAB_TOKEN` + `insteadOf`, PAT in Settings).
**Decision:** the bootstrap installs **glab** alongside gh (deb release from gitlab-org/cli — latest version via API with a fallback pin); the PR step detects the `origin` host (heuristic: "gitlab" in the hostname, covers self-hosted) and picks `glab mr create` / `glab mr note` vs `gh pr create` / `gh pr comment`, with a per-host URL regex (`/-/merge_requests/`). glab authenticates with `GITLAB_TOKEN` alone (env already injected by global credentials).
**Consequences:** the screenshots assets-branch is still GitHub-only (contents API) — on GitLab they remain only in the UI/Telegram with a clear log. Self-hosted is supported via the `GITLAB_HOST` env var (glab's convention): the bootstrap adds the `insteadOf` for that host (tolerates a scheme in the value), the PR step's detection compares the origin against that host in addition to the "gitlab" heuristic, and glab picks it up straight from the env.

## D-18 — Sandbox commits authored by the token owner (2026-07-21)

**Context:** the bootstrap set `Nexux Agent <agent@nexux.local>` as the git identity — task commits were not attributed to any real person (nor in the contribution graph, and GitHub can reject pushes with an unverified email if the user enabled private email protection).
**Decision:** after installing gh/glab, the bootstrap resolves the token owner's identity and sets it with `git config --system`: GitHub → `gh api user` with the **noreply** email (`{id}+{login}@users.noreply.github.com`, always valid and compatible with email protection); GitLab → `/api/v4/user` and its `commit_email` (respects the user's preference). The main repo's host is queried first (gitlab/`GITLAB_HOST` heuristic over the URL); the other token is the fallback, and `Nexux Agent` remains only as a last resort with a WARN.
**Consequences:** commits/MRs/PRs from tasks and the dev console are authored by the human who owns the token; if the token cannot read `/user` (unusual minimal scope), it degrades to the bot with a notice in the log.

## D-19 — Housekeeping and tests enforced by hooks, not prose (2026-07-31)

**Context:** the AGENTS.md housekeeping rules (update `PROGRESS.md`, add a `DECISIONS.md` entry, touch the module's `ARCHITECTURE.md`) and the sibling `*.test.ts` convention existed only as prose. `CLAUDE.md` *links* the docs, but a link does not load them: they entered context only if the agent chose to read them. Result: sessions that wrote code without seeing prior decisions and without creating tests.
**Decision:** four hooks in `.claude/settings.json` (versioned, not in `settings.local.json`, which is permissions only): `SessionStart` injects the full `DECISIONS.md` + `PROGRESS.md` (~178 lines, with defensive truncation); `PostToolUse` on Write/Edit warns if a `packages/*/src/*.ts` or `apps/web/src/{lib,services}/*.ts` has no sibling `.test.ts`; `Stop` warns if the working tree has code changes with no doc changes; `PreToolUse` on Bash runs `pnpm test` and **blocks** (exit 2) `git commit` when the suite is red. The first three are advisory (exit 0) — only the commit gate blocks.
**Consequences:** the gate costs ~2s per commit thanks to turbo's cache, and has two explicit escape hatches (`--no-verify` in the command, or `NEXUX_SKIP_TESTS=1`) for commits legitimately unrelated to code. The `Stop` hook carries a `stop_hook_active` guard so it cannot re-enter in a loop. The test warning is a heuristic based on the sibling-file convention: it does not cover UI components or `/api` routes (deliberately — they do not follow that convention), and it does not validate that the test is meaningful — only that it exists.

## D-20 — Stack node phases, derived before persisted (2026-07-31)

**Context:** a `StackNode` was `runMode: "docker" | "local"` plus five loose command columns and a `managesServices` boolean. That cannot express the common repo that installs on the host, brings infra up in Docker (`make docker-up`) and then runs the app — it needed **two nodes for one repo** plus an edge. Worse, `managesServices` recorded *that* a command launches background work but not *what*: the runner guessed liveness by scanning for any compose project in the node's directory, and `needsDocker` came back false for a `make dev` whose recipe is `docker compose up`, so sandboxes booted without Docker. Deep Makefile detection (shipped just before) could finally *tell* what a target does, but there was nowhere on the node to put the answer.
**Decision:** model a node as an ordered `StackPhase[]` — each phase a `role` (`install` → `build` → `services`/`run` → `stop`) and an `exec` (`host`, `compose`, `compose-extern`, `container`), carrying `composePath`/`provides`/`detached` when known. Ship it in two steps: **step 1 (this change)** adds pure `phasesOf(node)` that *derives* phases from the existing columns and moves consumers to read it, with no schema change and no writes; **step 2** persists a `phases` column, backfills, and retires the columns. `runMode` stays as a derived read-only value so the canvas, compose generation and sandbox filtering keep working untouched.
**Consequences:** deriving before persisting is the point — if `phasesOf` is wrong for some real project it surfaces while the columns are still authoritative, and the cutover is a swap behind one function instead of a migration plus a rewrite. `managesServices` still decides launcher-vs-app (the user's explicit answer outranks detection, which only supplies `detached` when nobody said), so step 1 is behaviour-preserving; verified equivalent on the launcher / app / docker-in-recipe cases. Three questions are deliberately left open in `specs/17-stack-phases.md`: whether the runner interleaves phases across nodes, whether the host runner starts executing `install`/`build` (today only the sandbox does — the canvas shows fields that do nothing locally), and whether repeated roles on one node are allowed.

## D-21 — Phases persisted, columns dual-written; Prepare split from Up (2026-07-31)

**Context:** D-20 landed phases as a *derivation* over the legacy command columns. Making them the stored truth is the half that actually removes the two-nodes-for-one-repo workaround, but a straight cutover would mean a migration plus a UI rewrite in one step, with a rollback that loses data.
**Decision:** add `StackNode.phases` and **dual-write**: both writers (`PUT /stack`, `POST /stack/detect`) persist phases and derive the command columns back from them via `columnsOf`, which is the exact inverse of `phasesOf`. Readers use `nodePhases`, which falls back to deriving for pre-cutover rows *and* for a malformed stored value — a bad JSON blob must never blank a node. The migration adds the column but does **not** backfill: reimplementing "read the node's cached detection to see what a `make` recipe does" in SQL would be a second, silently diverging copy of the rule, so `pnpm --filter @nexux/web stack:backfill-phases` does it with the real function. Separately, `install`/`build` phases now run on the host via `stackRunner.prepare` behind a **Prepare** button rather than inside `up`: a cold install takes minutes and Up is meant to be the cheap "start what is already prepared".
**Consequences:** the columns can drop in a later migration with nothing else to change. The inspector has to keep both faces in step — editing a command field re-derives the phases, editing a phase mirrors back into the columns — otherwise whichever half the user did not touch silently wins on save. A rescan re-derives phases *unless* they were edited by hand, since the rescan knows better about what a command does, not about what the user wants run. Verified end-to-end: `columnsOf(phasesOf(n))` is the identity for all 9 nodes in the local database, and the round trip holds in the browser in both directions. Two questions stay open in `specs/17-stack-phases.md` — ordering phases *across* nodes (today `up` still treats a node as a unit), and repeated roles on one node (representable and addable, but every reader takes the first).

## D-22 — Repeated phase roles are honoured, not collapsed (2026-07-31)

**Context:** D-21 left one hole open: a node could declare two `run` or two `services` phases — the editor even offers an Add button — but every reader took the first with `.find()`. The UI let the user create something the runner would silently half-ignore, which is worse than not allowing it.
**Decision:** readers iterate. Plural helpers (`runPhases`, `servicePhases`, `phasesWithRole`, `commandsOf`) become the default; `runPhase` survives only where a single answer is genuinely required — a sandbox has one preview port, not several. `startLocalNode` starts every run and service phase; `runStopCommands` runs every stop phase; `prepare` already iterated. Where a surface physically cannot hold two commands — the legacy columns and a repo's sandbox bootstrap slots — repeats collapse into an `&&` sequence (`&&` and not `;`, since a step whose predecessor failed has nothing to run against).
**Consequences:** `localProcs` is keyed by `nodeId#index` rather than `nodeId`, otherwise a second run phase would overwrite the first and leave it running but unstoppable from the UI. `status` collapses those processes back per node because the canvas keys status by node: a node reads as running while any of its phases is, and reports a running phase's pid in preference to a dead one. Log lines from a multi-phase node are suffixed with the role so two servers are distinguishable; a single-phase node logs under its plain name as before. Service launchers pair with stop phases by position, except that one stop phase is taken to undo whatever the node started. Verified in the browser: adding a second `run` phase to the `web` node produced `pnpm dev && pnpm dev:worker` in the legacy column, and removing it restored the original.

## D-23 — Env var values revealed on demand; stack env is copied, not referenced (2026-07-31)

**Context:** the sandbox settings panel could only add and blind-overwrite env vars — every value showed as `••••1234` with no way to read one back, so checking whether the stored `DATABASE_URL` was the right one meant retyping it. Entering a dozen keys meant a dozen round trips through a two-field form. Meanwhile the Stack canvas already held env for its nodes, invisible from the sandbox side.
**Decision:** three separate routes rather than widening the setup payload. `GET /env-vars/[id]/reveal` returns one plaintext value, fetched only when the user clicks 👁 or copy — putting values in `GET /setup` would have been less code but would ship every project secret on each panel load and park it in the React Query cache. `POST /env-vars/bulk` takes the *raw pasted text* and re-parses server-side; the client parse drives the preview only, so the two can never disagree about what gets written. `POST /env-vars/from-stack` **copies** a node's env into `ProjectEnvVar` instead of resolving it live at launch: a live reference would need merge-and-precedence rules in the launch pipeline against Settings secrets, credential tokens and repo-scoped vars, for a canvas whose env is mostly non-secret service config. One parser, not two — the stack inspector's `parseDotenv` gained multi-line quoted values and an `invalidLines` wrapper rather than growing a second implementation next to it.
**Consequences:** a revealed value can go stale under its own row — an edit or import changes the stored secret while the plaintext is on screen, and the mask is no signal (an overwrite of the same length looks identical). The editor bumps a `writeVersion` on every write and each row drops its cached plaintext when it changes; verified in the browser by overwriting a revealed var with a same-length value. Imports are per-scope: keys are matched against existing vars at the *target* scope, so the same key can live project-wide and repo-scoped without one silently clobbering the other. The bulk route rejects keys the parser accepts — `.` and `-` are legal in compose-style env but not in a shell var, and the single-var route already refused them. Because stack import is a copy, a later canvas edit does *not* propagate; re-importing is the way to resync, and the panel says so.

## D-24 — Sandbox status is reconciled against Docker, downgrade-only (2026-07-31)

**Context:** `Sandbox.status` was only ever written by our own actions — launch, pause, resume, destroy. Nothing observed the container itself, so a local sandbox killed from outside (OOM, `docker stop` in a terminal, Docker Desktop restarting) left the row reading `running` indefinitely. Everything the UI gates on that column then lied: a Live preview button and no Resume, while `sandboxReachable` — which *does* reach the container — failed every real action with "Sandbox is not running". Refreshing the page did not help, because the database was the stale part.
**Decision:** `GET /sandboxes` calls `reconcileLocalSandboxStatuses` before reading. It is deliberately narrow: **local provider only** (nothing to inspect for Civo/AWS without a cloud API call on every list), **`running` rows only** (a `pending` row's container legitimately isn't up yet), and **downgrade-only, to `paused`** — a stopped container is exactly what pause produces, so `resumeSandbox` can revive it with `docker start`. Two guards keep it from lying in the other direction: if `dockerAvailable()` is false nothing is touched (stopping Docker Desktop must not mark every sandbox paused), and a probe that *throws* leaves its row alone — only a definite "not running" downgrades. The decision half is `staleRunningSandboxIds`, a pure function taking probes as arguments, so the rule is unit-tested without a daemon.
**Consequences:** the list route now does I/O beyond a query — bounded by one `docker inspect` per running local sandbox, in parallel, and skipped entirely when there are none. The client polls every 15s while any local sandbox is `running`/`paused` (vs 3s for a real transition) so the flip appears without a manual refresh; `ACTIVE_STATUSES` stays as it was, since it also drives per-row polling and disabled states. Reconciliation is one-way on purpose: a container that is running while the row says `paused` is *not* promoted, because that is the state a half-finished resume leaves behind and guessing would race the resume itself.

## D-25 — Repo `.env` values are single-quoted (2026-07-31)

**Context:** D-24's sibling fix stopped a multi-line env var from truncating a repo's `.env`, but chose double quotes with escaped specials. That is wrong for the value that motivated the fix. A Firebase service-account credential is JSON already containing `\"` and `\n` that mean something *to JSON*; double-quoting escapes those backslashes again, and a reader hands back `{\"type\": ...}` — no longer parseable. Confirmed failing under both `node --env-file` and the `dotenv` package, i.e. exactly what a Next.js app in a sandbox uses.
**Decision:** single-quote instead. Dotenv treats a single-quoted value as literal, so a JSON payload passes through untouched. Real newlines are still folded to `\n` so the value stays on one physical line. A value containing a `'` cannot be single-quoted (there is no escape for it) and falls back to double quotes with escapes — acceptable because such values are not JSON payloads in practice. Bare values (no whitespace/quotes/`#`/`$`) stay bare so an ordinary `.env` still reads like one.
**Consequences:** the trade is that a *raw* multi-line value (a PEM pasted directly, not inside JSON) reads back with a literal `\n` rather than a real newline. That is the honest outcome: readers do not agree on `\n` expansion even inside double quotes — bash's `.` never expands it, while dotenv and Node do — so no single format gives every reader a real newline. Single quotes at least make all four readers agree on the same bytes, and the JSON case is the one that actually breaks. Verified byte-identical through `node --env-file`, `dotenv`, `python-dotenv` and `set -a && . ./.env`. Separately worth knowing: `export $(cat .env | xargs)` cannot load any value containing spaces regardless of quoting — xargs re-parses the quotes and strips backslashes — so it is not a supported way to read these files.

## D-26 — Local sandboxes get a terminal via `docker://` (2026-07-31)

**Context:** the row's "Open terminal" action was gated on `sandbox.publicIp`, so it never appeared for local sandboxes — they are Docker containers with no public IP. That left the local target, which is the free default in the wizard, as the only one you could not open a shell into, even though "Open in VS Code" already attached to the same container.
**Decision:** add a second remote scheme to the terminal server. A `cwd` of `docker://<container>[/path]` spawns `docker exec -it <container> bash -c "cd '<path>'; exec bash -l"`, alongside the existing `ssh://user@host[/path]`. The handoff prop from the Sandboxes tab now carries a **full cwd URL** rather than a bare `user@host` the manager prefixed with `ssh://` — the caller knows which scheme its sandbox needs, so the choice belongs there. Container names are matched with the same strict-charset approach as ssh targets (`[a-z0-9][a-z0-9._-]*`, path without quotes or spaces): a name that does not match takes no docker branch at all and falls through to a plain local shell, so metacharacters can never reach the host shell.
**Consequences:** the terminal picker, the row menu and the restored-tab pruning all key on "container name or public IP" instead of the IP alone, so a destroyed local sandbox's tab is pruned like a cloud one. The outer shell is `bash -c`, not `bash -lc`: as a login shell the session lands in `/` and the `cd` is lost — the inner `exec bash -l` still gives an interactive login shell and inherits the cwd. Since the server is started in-process from `apps/web/src/instrumentation.ts`, this change needs a **Next dev-server restart**, not just HMR.

## D-27 — Sandbox terminals get a `nexus` CLI, driven by an on-box manifest (2026-08-02)

**Context:** opening a terminal into a sandbox landed on a bare prompt. Nothing told you which repos were checked out, where they lived, which command booted each one, or what was already running — all of that existed only in the host's database, reachable from the dashboard's Processes panel and nowhere else. The information the person in the shell needed most was the information the shell had least.
**Decision:** bootstrap writes two files. `/opt/nexux/nexux.json` is a manifest — repos with their checkout dirs, and one entry per startable process (key, alias, command, cwd, port). `/etc/profile.d/nexux-cli.sh` defines a `nexus` shell function over it plus an ASCII banner. A manifest rather than a call back to the host API: the sandbox has no route to the dashboard (and giving it one would mean auth, and a container that stops working when the host is down), while a snapshot makes `nexus start web` answerable from inside the box alone. Start/stop deliberately reuse the *same* `/tmp/nexux-proc-<key>.{sh,pid,log}` paths and the same setsid + kill-by-recorded-PID discipline as `sandbox-process-manager.ts`, so a process started in the terminal is visible to and stoppable from the UI, and the reverse. Two supervisors with separate bookkeeping would leak orphans neither could reap.
**Consequences:** the manifest is a snapshot, so editing the Stack canvas leaves it describing commands that moved. Three things address that rather than hiding it: `nexus info` prints when it was written, `pushNexusCli()` (POST `…/sandboxes/<id>/cli`, "Sync terminal CLI" in the Processes panel) rewrites it from the current plans, and the bootstrap-time manifest is deliberately the weaker spec-derived one — `renderCloudInit` never sees the database, so it only knows each repo's `runCommand`, with no canvas keys or resolved ports until the first push. Re-sync is manual, not automatic on canvas save: it execs into a running box, which a save should not silently do. Two constraints shaped the script — the banner is guarded on `case $- in *i*` because `execRemote` runs every host→sandbox command through `bash -lc` (which sources profile.d) and the host regexes that stdout for `PID:` / `PREVIEW:` markers, and parsing uses `python3` rather than `jq`, which the base image does not ship. `nexus` is a function, not a script in PATH, so `nexus cd` can change the caller's directory. Verified end to end on `ubuntu:22.04`: start yields pid == pgid, stop leaves zero orphans, and `bash -lc` output stays banner-free.

## D-28 — Saved configs are importable env-var sources, by id and by copy (2026-08-02)

**Context:** three tiers of secret reach a sandbox — project env vars, saved credentials, allowlisted global Settings — but only the first was visible and editable in the wizard's env editor. The other two were resolved silently at launch by "first credential of this provider, oldest wins", so a workspace holding two Claude tokens (`claude-work`, `claude-personal`) gave no way to pin the *other* one for a single project short of pasting the secret back in by hand — and the token is exactly the value you cannot read off the panel, since it is masked everywhere.
**Decision:** make the source a **field on the existing add form** rather than a second import surface. The add row gains a picker that defaults to "custom value" — the flat KEY/value/scope entry, unchanged — and otherwise lists the saved configs grouped by kind. Choosing one fills the key (a saved `GITHUB_TOKEN` cannot be stored under another name), replaces the value input with the masked credential, and turns the button into "Replace" when that key already exists at the chosen scope. Adding a var is one concept with two sources, not two features; the bulk `.env`/Stack panel stays for multi-key pastes. Backing it: `GET …/env-vars/from-config` lists every LLM/git/Claude credential and allowlisted Settings row as `{id, group, key, label, valueMasked}`; `POST` takes ids back and writes `ProjectEnvVar` rows. The client only ever handles the **opaque id** — plaintext is resolved server-side in `apps/web/src/lib/env-presets.ts`, preserving the invariant that a secret crosses the wire only through the explicit per-var `reveal` endpoint, and meaning the preset path never puts a secret in a form field at all. Values are **copied, not referenced**, matching D-23: a live reference would need a new Prisma model and could not be edited or shown in the list. The catalogs are not re-declared — `env-presets.ts` composes `GLOBAL_ENV_SETTINGS`, `LLM_CREDENTIAL_ENV` and `GIT_TOKEN_ENV`, so a new provider added to `@nexux/sandbox` becomes importable with no change here.
A related gap closed alongside it: `PUT …/env-vars/<id>` took a value and nothing else, so the key was immutable and fixing a typo meant delete-and-recreate — retyping a secret that is masked everywhere and readable only through `reveal`. Both fields are now optional (at least one required): omitting `value` keeps the stored secret, so **a rename never requires reading the secret back**. Scope stays fixed, because moving a var between project-wide and repo changes *where it is written* (profile export vs the repo's `.env`), not just its name. Renaming onto a key already present at that scope is a **409**, applying the same `(projectId, repositoryId, key)` uniqueness the create route enforces in application code — SQLite treats NULLs as distinct in unique indexes, so the database will not catch it, and two rows exporting one name would leave the winner to row order.

**Consequences:** importing **inverts precedence**. Project env vars outrank everything at launch, so a copied `CLAUDE_CODE_OAUTH_TOKEN` starts shadowing the credential it came from, and the global panel begins reporting that credential as *"overridden by a project env var"* — correct, but surprising unless stated, so the panel says so in the copy under the list. The copy is also a snapshot: rotating the credential afterwards leaves the project stale, and nothing detects the drift. Two smaller rules exist because the data allows them: stale or deleted ids come back in `missing` rather than throwing (one dead id must not sink a valid import), and only `civo_api_key` / `telegram_*` stay excluded — they are provisioning secrets that must never leave the host, so a `setting:civo_api_key` id is rejected by the allowlist filter, not merely hidden from the listing. Covered by `apps/web/src/app/api/env-vars-routes.test.ts`, including an assertion that no plaintext appears in the listing response.

## D-29 — Log reachability is gated per source, not on `status === "running"` (2026-08-02)

**Context:** a local sandbox showed *"The instance is not running."* for its entire provisioning window — the one window where a user is actually watching. The panel picked `bootstrap` as the default source for local providers, but every in-instance source was gated on `status === "running"`, and the only tab with content in that state — `Sandbox.log`, where the host-side provisioner writes — was hidden for local containers on the reasoning of D-26, that a container has no Terraform run behind it. True about Terraform, wrong about the log: `runLocalProvision` writes `docker pull` / `docker run` output to that same column. The output was being produced correctly the whole time; the UI simply rendered none of it.
**Decision:** treat that tab as **the host-side provisioner's log**, not as Terraform's, and show it for both providers — labelled "Provisioning" for local, "Terraform" for cloud — defaulting to it whenever the sandbox is not yet running. For the in-instance sources, replace the blanket `running` gate with a per-source one: a new `bootstrapTailable` prop mirrors what `GET …/bootstrap-log` already enforces (a local container needs `instanceId`, a cloud instance needs `status === "running"` plus `publicIp`). The route had allowed mid-provision tailing for local since it was written — a container is exec-able the moment it exists, which is exactly when the bootstrap starts writing — so this removes a client-side restriction the server never had. The bootstrap branch is also evaluated **before** the `!running` fallback that was swallowing it; ordering, not a new condition, is what made that message unreachable.
**Consequences:** the "is this readable?" rule now lives in two places — the route and the prop — and they must agree; the prop is written as a mirror of the route's gate, with a comment saying so, because the alternative (an extra request per row just to ask) costs more than the duplication. The remaining sources (app, tunnel, dockerd, stack) stay gated on `running` and are correct to be: they read files that only exist once their services have started. The distinction is now explicit rather than incidental — bootstrap is readable as soon as the box exists, everything else once it runs. `SandboxSummary` already carried `instanceId` (it omits only `log`/`workDir`/`projectId`), so no payload changed. Verified against a real local sandbox held in `provisioning`, not just by reading code: the Provisioning tab streamed `pulling ubuntu:22.04` → `creating container`, and Bootstrap followed `installing cloudflared` live with the `installing…` badge. Note this narrows D-26's "hide Terraform for local" to "relabel it" — the log was never Terraform-specific.

## D-30 — The sandbox drawer's UI state lives in the URL; its width lives in localStorage (2026-08-02)

**Context:** the sandbox setup drawer is a six-step wizard that fills a fixed `sm:max-w-xl`. Three complaints, one root cause — the drawer kept no state of its own: it could not use the space on a wide monitor, a stray click on the page dismissed it and silently discarded a filled-in wizard (Base UI's `Dialog` defaults `disablePointerDismissal` to `false`), and a refresh dropped the user back on step 1.
**Decision:** split the state by what it means. **Which step you are on** is navigational, so it goes in the URL (`?sandboxSetup=1&sandboxStep=<key>`) alongside the existing `?tab=`/`?section=` params, written with `history.replaceState` so Back leaves the page instead of walking through every step visited. **How wide the drawer is** is a per-machine preference, so it goes in `localStorage` as pixels, not a viewport fraction — the drawer holds forms whose comfortable width does not scale with the monitor. **Whether there are unsaved changes** is derived, not stored: `SetupEditor` compares a `JSON.stringify` of `{config, mcpJson, repoSetups}` against a snapshot taken on load and reset after each successful save, and reports it upward so the sheet can `cancel()` the dismissal and raise a confirm. Only `outside-press` and `escape-key` are intercepted — the explicit X and the footer buttons close as asked, because a guard on a deliberate close is a nuisance, not a safety net. URL persistence is opt-in via `persistStepInUrl` so the Run dialog, which mounts the same sheet transiently, does not fight the Sandboxes tab for the same params.
**Consequences:** `SheetContent` gained an optional `resizeHandle` prop (right/left sides only) and callers now own the width via `style`, which required dropping the hardcoded `sm:max-w-xl` in favour of `sm:max-w-none` — any future caller wanting the old cap must say so. `?sandboxStep=` deliberately **survives** closing the drawer: `SetupEditor` stays mounted behind the closing animation, so deleting the param there would leave the URL disagreeing with the step the wizard is still on and make reopening look like a reset. The width clamp treats `innerWidth <= 0` as "not measured yet" and skips the upper bound — clamping against a zero viewport collapsed every restored width to the minimum, so a resized drawer reopened tiny; `clampPanelWidth` is exported and unit-tested for exactly that case. Dirty-tracking by serialization is O(form) per render and would be the wrong tool for a large form, but this one is a few dozen fields and it avoids threading a dirty flag through every input. Verified in the browser: restore-on-refresh at a non-default step, drag-resize persisting across a reload, and both the outside-click and Escape paths raising the confirm with "Keep editing" preserving the edit.

**Amendment (2026-08-02):** restoring the step was only half of restoring the wizard. What a step *shows* has to survive a reload as faithfully as which step is open, and one answer could not: `SandboxConfig.provider` is `civo | aws`, so "local" — the Type step's answer — had nowhere to persist, and `destination` re-initialised from the saved provider on every mount. A user who picked Local and refreshed on a later step came back to that step with the destination flipped to a cloud instance, and Launch would have provisioned a billed VM. The destination now rides in the URL beside the step (`?sandboxTarget=`), which is the only place it can ride without a schema column; it is read once on mount, and the URL mirrors it thereafter. This is a workaround, not a fix — reopening the drawer from a link with no `?sandboxTarget=` still falls back to the saved cloud provider. The same code hid a second defect: `steps.findIndex` returns `-1` for a step the destination hides and `Math.max(0, …)` turned that into step 1, so a stale `?sandboxStep=machine` on a local target reset the wizard rather than resolving to the next step that still exists. Both rules moved into `apps/web/src/lib/sandbox-setup-wizard.ts` — the resolution order matters (the destination decides which steps exist, so it settles before the step does) and it is not expressible in a component this app cannot render under `tsx --test`. Pinned by 16 tests, including a round-trip over every destination × step pair.

## D-31 — Configuration exports carry keys, not values, unless sealed (2026-08-02)

**Context:** replicating a local install onto a 24/7 VM needs the configuration to travel — projects, repos, stack canvas, sandbox config, roadmap, schedules. Copying `dashboard.db` already does that and is the honest fallback, but it also carries `Sandbox.instanceId` / `publicIp` / Terraform `workDir` describing infrastructure the destination cannot manage, and absolute host paths (`/Users/dev/...`) that do not exist on Linux, with no chance to remap either. The sharper constraint: `ENCRYPTION_KEY` is read in `@nexux/config` and **never consumed** — there is no cipher anywhere in the app — so `ProjectEnvVar.value`, `CloudCredential.data` and `Settings.value` are plaintext on disk, despite schema comments reading `// encrypted`. An export is therefore a file of API keys unless something is done about it, and a file travels in ways a database does not.
**Decision:** a three-layer split, with secrets opt-in and sealed. Layer 1 (portable configuration) always exports. Layer 2 (secrets) requires `includeSecrets` **and** a ≥12-char passphrase, and the result is scrypt + aes-256-gcm sealed before it leaves the process — transport encryption for the artifact, not encryption at rest for the database, which stays a separate fix. Layer 3 (machine state: `Sandbox`, `SandboxProcess`, `SandboxTask`, `EmbeddingIndex`, `OAuthState`, `GitHubIssue`) is excluded unconditionally, `includeSecrets` or not: importing a `Sandbox` row hands someone a Destroy button aimed at another install's VM, and an `EmbeddingIndex` row without the LanceDB table it describes makes the destination believe a project is indexed. Secretless exports still emit env var **keys** with `value: null` and credential **shells** (`id`, `name`, `provider`, `data: null`) — the credential FKs on `SandboxConfig` encode which of two tokens a project pinned (D-28), which is configuration, not a secret; dropping them silently reverts the project to "first credential of this provider, oldest wins". Host paths become `{ root: "pathRoot", rel }`, with paths outside the common root kept `{ root: "absolute", abs }` rather than mangled. Two verbs: `GET` for the secretless case so the UI is a plain download link, `POST` for anything with a passphrase — a passphrase in a query string lands in server logs and browser history, and both ends enforce the split.
**Consequences:** the export validates against its own zod schema on the way *out*, not only on the way in, so a collector that drifts fails while the user is still at the keyboard rather than after they have moved the file. `pathRoot` is the longest common **directory** prefix, computed segment-wise — `/a/foo` and `/a/foobar` share `/a`, not `/a/foo` — and a single path yields its parent, or a one-project export would set `pathRoot` to that project's own `workspacePath` and lose its directory name. Canvas `StackNode.env` and `SandboxConfig.mcpServers` follow the secret rule rather than riding along as ordinary Json: both routinely hold API keys. Schedules export with `enabled` as-is so the file stays an accurate record of the source, and it is **import** that forces them false — a schedule arriving live would provision sandboxes and open PRs while the source instance still does the same on its own timer. Conversations are excluded by default (high volume, a log rather than configuration) behind `includeConversations`; they are fetched in a separate query because Prisma types a relation off the literal `include`, so a ternary there erases `messages` from the result type for both branches. Import is deliberately not built here: this is one-directional and manual, and two-way sync would need per-row versioning the schema does not have. Pinned by `apps/web/src/app/api/export-routes.test.ts`, whose load-bearing assertion is that none of five planted secrets appears anywhere in a secretless export.

## D-32 — Import upserts by id, and the preview is the writer (2026-08-02)

**Context:** the export side of D-31 produced a document; reading it back needed a policy for ids, for rows the file does not carry, and for a preview the user can trust before a destructive operation. Every model uses `cuid()`, so two strategies were available: regenerate ids on import (no collisions, but every FK needs remapping and a second import of an updated file duplicates everything), or preserve them and upsert.
**Decision:** preserve ids, upsert by id. A re-export/re-import then *converges* instead of accumulating, which is what makes Mac → VM → edit → Mac coherent. Colliding cuids across unrelated installs are not a practical risk, so a matching id means the same row — which is what upsert assumes. Two modes: `merge` (additive, the default; rows here but absent from the file are left alone) and `replace` (rows absent from the file are deleted, scoped to the projects in the file, never touching Layer 3 or the shared catalogs). The **dry run and the write are one function** parameterised on `dryRun` — a preview computed by different code than the write is a preview that eventually lies, and this preview is the only thing between the user and `replace`. Writes stay sequential rather than one transaction, matching `env-vars/bulk`: SQLite serialises writes anyway, and a partial import that reports how far it got beats a rollback that hides the malformed row. Schedules always land `enabled: false` with their run bookkeeping cleared, and a secretless file never blanks a secret already on the destination — importing shells would otherwise wipe the very tokens whose references it is preserving.
**Consequences:** two constraints surfaced only under test. **`commonRoot` must be a strict ancestor of every exported path**: the ordinary layout — repos inside the project's workspace — makes that workspace the longest common prefix, giving it `rel: ""`, erasing the project's own directory name, and resolving to the bare destination root on import. Caught by the round-trip test on seeded data and confirmed against five real projects, two of which (`cli-maker`, `product-hub`) have a repo path equal to the project path and would have imported into the wrong directory. **`Agent.name` and `Skill.name` are globally `@unique`**, so the same name under a different id is a real conflict where upsert-by-id throws; the incumbent wins (its name is what joins and `.claude` context reference) and the file's id is remapped onto it for that import's joins, with a warning. Every row behind a `@unique` FK — `SandboxConfig.projectId`, `ProjectDocument.projectId`, `RepositorySetup.repositoryId`, `Phase(projectId,key)`, `ProjectDocumentSection(documentId,key)` — is keyed on that constraint rather than the row id for the same reason. A schema version newer than the destination's is a hard refusal (the file may carry columns that do not exist here, and dropping them silently yields a project that looks imported and is not); older only warns, since migrations are additive in practice. A 422 carries the same plan shape a dry run returns, so a refusal renders exactly like a preview. Repositories always arrive `cloneStatus: "pending"` — the checkout is the destination host's business. Round-trip equality holds byte-for-byte except `schedules[].enabled`, the one field import deliberately rewrites.

## D-33 — On-box sandbox paths spell `nexus`; the old `nexux` spelling stays as a compat shim (2026-08-02)

**Context:** the in-sandbox CLI is `nexus`, but everything it touched on disk was spelled `nexux` — `/opt/nexux`, `/etc/profile.d/nexux-{env,cli}.sh`, `/tmp/nexux-proc-*`, and the agent user itself. The banner rendered `NEXUX` in ASCII above a prompt that answered to `nexus`. The complication is that these are not strings in a UI: they are live paths on provisioned boxes, and `/tmp/nexux-proc-<key>.{sh,pid,log}` is a contract deliberately mirrored byte-for-byte between `sandbox-process-manager.ts` on the host and the `nexus` function inside the box (D-27). Renaming one side alone yields two supervisors with separate bookkeeping and orphans neither can reap.
**Decision:** rename the on-box surface to `nexus` — checkout root, profile.d files, manifest, workspace file, proc paths, bootstrap/dockerd logs, and `AGENT_USER` — and keep the old spelling reachable rather than cutting it off. Bootstrap moves `/opt/nexux` to `/opt/nexus` once and leaves a symlink pointing forward, so stale PID files, a VS Code window reopened on its last folder, and shell history all keep resolving. `nexux-env.sh` becomes a symlink (a stale *copy* would keep exporting superseded values, since profile.d sources both); `nexux-cli.sh` is deleted outright rather than symlinked, because profile.d sourcing both would define the same functions twice. Legacy `.bashrc` lines are rewritten in place — the source guards grep for the new name, so without the rewrite each box would source the file twice. Host-side reads (liveness, stop, log tail) and the in-box CLI both check the legacy proc paths, so a process started before the upgrade stays visible and killable; writes only ever use the new path, so the old set drains as processes restart. The `nexux()` shell alias survives as muscle memory. Deliberately **out of scope**: the `@nexux/*` package scope, the repo name, the `nexux/<slug>` git branch prefix, the host `.nexux/` data dir, the dashboard container's own `nexux` user, and the write-only `nexux-sandbox=1` Docker label — none are on-box paths, and renaming them is a separate change with its own blast radius.
**Consequences:** the migration is the risk, not the rename. Two guards make it idempotent — `! -L` on the outer test and `[ -e /opt/nexus ]` on the inner — and they are redundant by design: cloud-init reruns, and either one alone prevents the destructive case. Removing *both* lets a second `mv` succeed *into* the now-existing directory, burying the compat symlink at `/opt/nexus/nexux`; `readlink` still reads correctly at that point, so the stray directory entry is the only observable symptom, and the test asserts on it. The migration tests execute the extracted block against real temp directories rather than asserting on script text, and deliberately run **without `set -e`**, matching how cloud-init invokes it — under `set -e` the redundant `mv` aborts the run and masks exactly the bug worth catching. A box where both `/opt/nexux` and `/opt/nexus` exist as real directories is treated as unmodelled: bootstrap warns and touches neither, rather than picking a winner and deleting someone's checkouts.

## D-34 — The server image assumes a private network, and says so (2026-08-02)

**Context:** running the dashboard 24/7 on a VM needed the container image to be deployable, but the app has **no authentication of any kind** — no login, no session, no middleware. Every `/api` route is open, `GET /env-vars/<id>/reveal` returns stored secrets in plaintext, the terminal WS `exec`s into sandboxes, and `/api/export` will hand over the whole configuration. That is fine under D-01 (local-first, single user, trusted machine) and stops being fine the moment a port faces the internet.
**Decision:** treat the private network as the security boundary rather than bolting on half an auth layer. Compose publishes to `${NEXUX_BIND:-127.0.0.1}`, so a careless `docker compose up` exposes nothing off-box; reaching a remote install means putting it on Tailscale and binding to that interface. Real authentication is a *feature*, not a deployment setting — it would have to cover the API routes **and** the terminal WS, which does not share Next's request pipeline — so it is deliberately out of scope here and the constraint is documented at the top of the Dockerfile, the compose file and `docs/DEPLOYMENT.md` instead of being left implicit. Local (docker-in-docker) sandboxes are likewise **not** supported in this image: enabling them means mounting the host's docker socket, which is root-equivalent on the host, and the provider whose whole purpose is a free local alternative is not worth that on a remote box. Cloud sandboxes are, so `terraform`, `ssh` and `git` are installed.
**Consequences:** three real defects surfaced while making the image actually work. **`NEXUX_DATA_DIR` was never set**, so `getConfig().dataDir` fell back to `~/.nexux` — an image layer — putting the LanceDB indexes *and* the installation's sandbox SSH keypair (`<dataDir>/ssh`, `keys.ts`) outside the volume; every `up --build` silently dropped the search indexes and regenerated the key, locking the install out of every sandbox it had already provisioned. Verified by fingerprinting the key across a real rebuild: identical with the fix, and `/home/nexux/.nexux` without it. **`packages/sandbox/package.json` was missing from the builder stage** even though `apps/web` depends on `@nexux/sandbox`, so the workspace install was incomplete. **Port 3002 was never published**, so "Open terminal" had nothing to connect to — it needs `NEXUX_WEB_ORIGIN` to match the browser's URL too, or the WS upgrade is refused by CORS, which presents as a terminal that hangs while everything else works. Also corrected: `.env.docker.example` claimed `ENCRYPTION_KEY` "encrypts stored API keys". It does not — it is read by `@nexux/config` and never used, so `/data` *is* the secret store and the file now says that plainly rather than implying a protection that does not exist. A side effect worth knowing: a VM-produced export carries a populated `meta.schemaVersion` (the image sets `NEXUX_MIGRATIONS_DIR`, so `_nexux_migrations` exists), unlike a dev-server export where it comes back empty and import comparison degrades to a warning.

## D-35 — A host's registry login is a chosen credential, checked before the VM exists (2026-08-03)

**Context:** a host bootstrap died on `Error response from daemon: ... unauthorized` after minutes of installing Docker and Tailscale, with a log that blamed the image ("is the package public?") rather than the token. Three separate faults produced that. The registry login was *inferred* — `resolveGitCredential()` with no id, i.e. whichever git credential was saved first, which picks the wrong account as soon as there is more than one and picks a *GitLab* token for GHCR if that one is older. Nothing verified the token before terraform ran, so the first evidence arrived on a billing instance. And the credential pickers the create form did have (cloud, Tailscale) had no registry equivalent at all.
**Decision:** the host row stores `registryCredentialId` alongside its cloud and Tailscale ones, the form picks it, and both the resolve and the pull check run **before** `nexusHost.create` — a wrong token must cost nothing. The mapping from git host to registry (`github → ghcr.io`, `gitlab → registry.gitlab.com`) is a *default*, not a rule: a credential carries an optional `registryHost` in its JSON `data`, so a self-hosted GitLab or GitHub Enterprise serving its own registry is expressible without a schema change, and the form offers exactly the credentials that can log in to the registry the image reference names. The pull check reads the token endpoint from the registry's own `WWW-Authenticate` challenge instead of hardcoding `ghcr.io/token`, so GHCR, GitLab and a self-hosted registry are one code path. Verification is deliberately asymmetric: **any answer other than a definite 401/403 passes**, because a registry unreachable from *this* laptop says nothing about the host, and refusing on a network hiccup is worse than letting the pull fail on the instance.
**Consequences:** the interesting case is a credential that is rejected for an image anyone could pull anonymously — an expired token nobody chose. Failing there would block a working public image, so an *unchosen* credential that gets a 401 is retried anonymously and dropped if that succeeds; a credential the user **picked** still errors, since quietly ignoring the choice would hide that it does not work. `resolveGitCredential` also grew an `id` in its return, because host code must be able to tell "resolved what I asked for" from "silently fell back" — the fallback is correct for a sandbox and wrong for a registry login. The preflight is tested against `assertImagePullable` directly rather than through `POST /api/hosts`: the cases worth covering are the ones that *pass*, and a route-level test of those would let `createHost` reach terraform and provision a real instance.

## D-36 — A host updates itself through a request file, never a docker socket (2026-08-03)

**Context:** updating a host means `docker compose pull && up -d` in `/opt/nexus-host`. From the local install that is easy — it holds the SSH keypair provisioning registered, so it just runs the command. From the host's *own* dashboard it is not possible at all: the container has no docker socket, and the keypair that opens root on the box lives on the laptop that provisioned it, not on the host. The obvious fix, mounting `/var/run/docker.sock`, is the one thing that must not happen here: the socket is root-equivalent on the host, and this app has **no authentication of any kind** (D-34), so anything that reaches the dashboard would reach root on the machine.
**Decision:** bootstrap installs a root-side `nexus-update.service` and a `nexus-update.path` unit, and bind-mounts a single control directory into the container. The app writes a request file; the unit does the pull. The capability the container gains is exactly "ask to be updated" — it cannot pass a command, a path or an image, so a compromised dashboard gains nothing a reboot would not. A **path** unit rather than a timer, because an update should start when it is asked for rather than up to a minute later. Never `down` then `up`: the named volumes hold the database, the credentials and the search indexes, and `down -v` would take them with it. The self-update path deliberately **never reports success** — `up -d` recreates the container serving the request, so the process handling it is killed mid-pull by design; "requested, this page will drop out for a minute" is the honest message, and the updater's log is the only record of what happened.
**Consequences:** two ordering rules are what make it re-runnable, and both are failure modes rather than tidiness. The updater removes the trigger file **before** pulling: `PathExists` re-fires for as long as the file exists, so an updater that consumed it last would update in a loop. Cloud-init clears a stale request **before** arming the unit: cloud-init re-runs, and a request left from before a reboot would otherwise start an update nobody asked for the moment the machine came back. The generated script is *executed* in a test against a stub `docker` on PATH rather than pattern-matched — the earlier tests assert it says the right things, this one asserts it does them. Hosts provisioned before this change have no control mount; `requestSelfUpdate` detects the ENOENT and names both ways out (update from the local install, or run `/opt/nexus-host/update.sh` on the machine) rather than surfacing a filesystem error. The SSH half stays a direct command because that side has a shell and can report what the pull actually did — and unlike the self-update path it survives its own effect, since recreating the container does not touch sshd.

## D-37 — A host clones into a declared volume, and paths it cannot write are refused up front (2026-08-03)

**Context:** every repository on a Nexus host failed to clone with `EACCES: permission denied, mkdir '/opt/workspace'`. The path came from the user, who typed what the import form's placeholder and `DEPLOYMENT.md` both suggested — but nothing on a host ever made it real. The container runs as uid 1001 (`nexux`) and mounted exactly two volumes, `nexux-data:/data` and the D-36 control directory; `/opt` is root-owned image layer. So the path was unwritable, and had it been writable it would have been *worse*: anything outside a declared volume is discarded when `up -d` recreates the container, which D-36 does on **every** update. The dashboard would have reported a successful clone and lost the checkout at the next pull.
**Decision:** the host declares `nexux-workspace:/workspace` and passes `NEXUX_WORKSPACE_ROOT` to the app; `getConfig().workspaceRoot` falls back to `~/nexux-workspace` for local installs, so the app always has one answer to "where do checkouts go". The Dockerfile creates `/workspace` chowned to `nexux` **specifically so the mountpoint's ownership seeds a fresh named volume** — docker copies image-directory permissions onto an empty volume, which is what makes this work with no host-side chown. An import that names no root now rebases onto that workspace instead of refusing: the paths in the file describe the *source* machine, and on a host there is exactly one safe destination, so making the user supply it only invited the wrong answer. `cloneRepository` walks to the nearest existing ancestor and checks `W_OK|X_OK` before running git.
**Consequences:** the preflight exists because git's own error is the least useful sentence available — it names the syscall, not the reason the path was never going to work, so the message now names the blocking directory *and* the workspace to use instead. Directory browsing starts at the workspace rather than `shell.home`, which inside the container is not writable by the app's uid, and creates it on demand so a fresh install does not get "Cannot read directory" for the one path it just recommended. This reverses the previous contract that a rootless import is a 422 — its test was rewritten rather than deleted, since the behaviour is now the opposite and worth asserting. Hosts provisioned before this change have no workspace volume: re-bootstrapping adds it, and their existing rows still point at unwritable paths, which the preflight now explains instead of leaving as a bare `EACCES`.

## D-38 — Update outcomes are read back from evidence, not claimed at request time (2026-08-03)

**Context:** neither update surface could answer the questions that make "Update" usable: what build is running now, was there anything newer, and did the update finish? The image carried no version identity at all (`.dockerignore` excludes `.git`, so nothing inside the build can know its own SHA), the SSH update said "Updated and restarted" even when the pull found nothing, and the self-update path — honestly, per D-36 — ended at "requested" and never said another word.
**Decision:** three mechanisms, all evidence-based. (1) **Identity is baked at build time**: CI passes `NEXUX_GIT_SHA`/`NEXUX_VERSION` as build args, and the Dockerfile writes a `date` stamp on every build (placed after the app COPYs so the layer re-runs exactly when content changed) — surfaced by `/api/version`, shown on the host's own Settings card. (2) **The SSH update proves change**: it echoes the running container's image id before and after, and only claims "already up to date" when both ids were captured and equal — a missing echo degrades to the generic message, never to a false negative. (3) **Self-update completion is detected, not reported**: the card captures the last "finished" stamp in the updater's append-only log at click time, polls until a *different* stamp appears, then compares `/api/version` before/after — changed ⇒ updated, unchanged ⇒ nothing newer, a FAILED line in that run ⇒ failure with the log auto-opened. D-36's constraint stands untouched: the request still reports nothing, because the app serving it dies mid-update by design. There is deliberately **no separate "check for updates"**: the pull is the check, and a pull that finds nothing restarts nothing, so the one button answers both questions.
**Consequences:** completion must be "a stamp I have not seen before", never "a stamp exists" — every past update left one in the append-only log, and the tests pin exactly that comparison (including a run still in progress, whose log shows a new "started" but the *old* "finished"). A 15-minute ceiling stops the card from claiming progress forever and points at the log instead. Hosts on images from before `/api/version` answer 404; the client maps that to "unknown build — updating fixes that" rather than an error. The build-date layer means two otherwise-identical local builds get different identities, which is the right reading of "did the update change anything" for `:edge`-style tags whose version string never moves.

## D-39 — The sidecar ships the Next it was built with, and boots without reading its config (2026-08-03)

**Context:** the Windows bundles from the 2026-08-03 release run were both broken, in two different ways, and `~/.nexux/native.log` (the on-disk log the app writes because GUI apps on Windows have no visible stderr) named each one. The NSIS build started fine and then failed every render with `Error: renderToPipeableStream is not implemented`; the MSI build died at boot with `EPERM: mkdir 'C:\Program Files\Nexux\sidecar\node_modules\next\next-swc-fallback'`. Neither is a Windows bug. `.next/diagnostics/framework.json` said the bundle was built by Next **16.2.6** — the lockfile's version — while `sidecar/node_modules/next` was **16.3.0**, published 90 minutes before that build ran. `pnpm deploy --legacy` (forced, since the workspace is not injected) re-resolves every range from scratch and warns as much: *"Shared workspace lockfile detected but configuration forces legacy deploy implementation."* So `"next": "^16.2.6"` shipped a runtime newer than the one that produced `.next`, and 16.3.0's server calls `renderToNodeFlightStream`, which requires an export 16.2.6's page bundles do not have. The MSI failure is a second-order effect of an existing size optimisation: every `@next/swc-*` binary is pruned, so loading `next.config.ts` at boot — Next transpiles it with SWC — falls back to *installing* `next-swc-fallback` into the app's own install directory, which is writable under `%LOCALAPPDATA%` (NSIS) and not under `C:\Program Files` (MSI).
**Decision:** pin `next` to an exact version in `apps/web/package.json`, and have `start.js` do what Next's own standalone `server.js` does — set `NODE_ENV=production` and `__NEXT_PRIVATE_STANDALONE_CONFIG` from `.next/required-server-files.json`, the config Next already resolved at build time — then delete `next.config.*` from the deployed sidecar. Pinning is the fix rather than `--frozen-lockfile`, which was tried and **does not work**: legacy deploy ignores it and still resolved 16.3.0. Feeding the config in removes the only reason the runtime needed a compiler, so the app no longer writes into its own install directory at boot. `build-sidecar.ts` then asserts the built and shipped Next versions match and fails the build if they drift, because the version pin is a convention and the assertion is the thing that holds.
**Consequences:** the failure this prevents is silent by construction — nothing in the build is wrong, nothing logs a warning, and the drift only becomes visible as a blank window on an end user's machine, hours after CI went green. That is why the guard lives in the build (fails the bundle) *and* in `tests/parity.test.ts` (fails the PR): the parity test catches a `^` reintroduced into the manifest, the build assertion catches drift the manifest cannot express. The pin has an obvious cost — Next upgrades are now deliberate, not incidental — which is the intent, since the sidecar's `.next` output and its runtime are one artefact. This was never platform-specific: the macOS build from the same day ran its deploy at 22:17 UTC, well after 16.3.0 was published, so it carries the same defect regardless of how it appeared to behave. Windows was simply the platform where a *second*, genuinely OS-dependent fault — a read-only install root — turned the same bundle into a different symptom. Inspecting what the installers actually carried surfaced a third, unrelated leak worth the same treatment: `pnpm deploy` copies `apps/web/.env`, so a locally built installer shipped the build machine's secrets, and not inertly — `@next/env` skips only keys already in `process.env`, and `lib.rs` passes just `PORT`, `HOSTNAME`, `NEXUX_*` and `DATABASE_URL`, so anything else in that file was loaded into every install. `.env*` is now stripped alongside `next.config.*`: the sidecar's configuration is what `lib.rs` hands it, and nothing the build machine happened to have lying around.

## D-40 — The sidecar dies with the app, and the window never shows a server it did not start (2026-08-03)

**Context:** two Windows symptoms that looked like packaging bugs were the same defect wearing different clothes. The NSIS installer failed with `Error opening file for writing: …\sidecar\node_modules\@lancedb\…\lancedb.win32-x64-msvc.node`, leaving 6,824 of 44,405 files on disk once the user answered the Abort/Retry/Ignore prompt. Then the MSI build came up **unstyled**, serving a half-installed app — because its own sidecar had died with `EADDRINUSE` on 3030 and 3032 while a sidecar from the *previous* install was still listening. The common cause: `RunEvent::Exit` kills the child on a normal quit, but nothing runs on a `TerminateProcess`, so an app closed by Task Manager, a crash, or an installer leaves `node.exe` alive — holding the ports and an open handle on its own `node_modules`. Compounding it, `wait_for_port` only asked "does something answer on 3030?", so the app happily pointed its window at a stranger's server.
**Decision:** two independent guarantees, because either alone still fails. The kernel enforces the lifetime: on Windows the spawned child is assigned to a job object with `KILL_ON_JOB_CLOSE`, whose handle is deliberately never closed, so however this process dies the sidecar goes with it. And the app refuses to *guess* whose server it is talking to: if 3030 is occupied **before** the spawn it does not start at all, since the sidecar would die with `EADDRINUSE` anyway and the readiness probe cannot tell ownership afterwards. To say any of this, the window now opens on the bundled placeholder instead of `http://127.0.0.1:3030` — which also removes the browser connection error that every launch showed for its first seconds — and `lib.rs` writes failures onto it through `window.__nexuxStatus`.
**Consequences:** the port check is what makes the readiness probe sound: it is only because the port was free at spawn time that "something answers" can be read as "our sidecar answers", so the two changes are one mechanism, not two features. Startup failure is now surfaced three ways that must stay in sync — the port precondition, a `Terminated` event flipping an `AtomicBool` the wait loop watches, and the timeout — and each writes to both the log and the screen; parity tests pin the placeholder hook on both sides, since a status channel with one half missing fails silently by construction. The job object is Windows-only on purpose: orphans happen on macOS and Linux too, but nothing there holds a mandatory file lock, so the failure that motivated this cannot occur. A pre-existing install still needs its stale sidecar killed once by hand — the guarantee starts with the first build that has it, and cannot reach back to an orphan the previous build left behind.

## D-41 — A shell is chosen per terminal, because Windows has more than one answer (2026-08-04)

**Context:** on Windows no terminal opened at all. `getConfig().shell.binary` walked `$SHELL`, `/bin/zsh`, `/bin/bash` and fell back to `/bin/sh` — none of which exist there — and the spawn passed `-i`, a POSIX flag `cmd.exe` and `powershell.exe` reject. The deeper problem is that the question has no single answer on that platform: a machine has `cmd`, Windows PowerShell, possibly PowerShell 7, and one shell per installed WSL distro (this one has five), and *which* of them a project needs is a property of the project, not the machine — the user's code lives in WSL while the app runs on the Windows side.
**Decision:** the shell becomes a per-session id (`powershell`, `cmd`, `pwsh`, `wsl:<distro>`, `posix`) sent on the WebSocket, with a workspace default in `Settings` under `terminal_default_shell` and a per-pane override stored with the pane. `@nexux/config` loses `shell.binary` entirely: enumerating shells needs `wsl.exe --list`, which is a subprocess and a machine question, so it belongs in `@nexux/terminal`'s `shells.ts` — config keeps only `home`. The pty server never reads the database; the client resolves "no choice" to the configured default and sends an explicit id, so the server only ever runs what it is handed. An id it cannot run (a distro since removed, state restored from another machine) opens the default and says so **in the session**, because a terminal that silently opens the wrong shell is worse than one that explains itself.
**Consequences:** WSL is the case that shapes the design. node-pty's `cwd` must be a *Windows* directory, so the Linux working directory cannot be passed that way — it becomes a `cd` inside the distro, and `toWslPath` translates what the UI stored (`E:\workspace\x` → `/mnt/e/workspace/x`, `\\wsl.localhost\<distro>\x` → `/x`). The launcher is `sh -lc` rather than `bash -lc`: verified against all five distros here, `docker-desktop` is busybox and died with "bash: not found" until the command stopped assuming bash, so it now `exec`s bash only where it exists. That same distro cannot see the host's drives at all, and the `cd`'s existing `2>/dev/null` tolerance is what turns "cannot reach /mnt/e" into a working shell in its own home rather than a dead session — so it is listed like the rest instead of being filtered out. The session tests in `terminal-server.test.ts` assert `pwd`, `stty size` and brace grouping, which no Windows shell provides; they now skip on win32 rather than hanging the run, and the platform-independent half moved to `shells.test.ts`, which runs everywhere.

## D-42 — A sandbox name is bounded, because Docker hands it to sethostname (2026-08-04)

**Context:** every local sandbox died with `OCI runtime create failed: runc create failed: … error during container init: sethostname: invalid argument` — an error that names neither the limit it hit nor the value that broke it, and arrives after the image pull, so it reads as a Docker or runc problem rather than a name problem. The container left behind gave it away: `nexux-wsl.localhost-ubuntu-26.04-home-developer-workspace-acme-dashboard-settings-micro-frontend-901e4b`, 102 characters. `launchLocalSandbox` passes the instance name to both `--name` and `--hostname`; Docker validates the former and passes the latter straight through to `sethostname(2)`, which rejects anything past `HOST_NAME_MAX` (64) with EINVAL. The name was `nexux-${safeSlug(project.name)}-${id}` with no bound, and a project is commonly named by its full path — here a WSL UNC path, which is long before the project even starts.
**Decision:** `sandboxInstanceName()` in `@nexux/sandbox` owns the construction and caps it at **63** — the number that satisfies both `HOST_NAME_MAX` and the 63-character DNS label limit, so the same name remains legal for the cloud providers that also take it. It trims the slug from the **left**, because the tail of a path is what identifies a project while the head is the share, distro and home directory every project on the machine shares; cutting the other way would make every sandbox look alike. A cut that lands mid-segment drops the partial leading segment when a whole one survives, so the result reads as path segments rather than debris (`…developer-workspace-…` → `workspace-…`, not `r-workspace-…`).
**Consequences:** the unique suffix is preserved by construction — the budget is computed *after* reserving the prefix and the id — so truncation can never collide two sandboxes of the same project, which is the failure mode a naive `slice(0, 63)` would introduce. Verified against the real name: 103 characters reproduces the user's exact error, and the 61-character replacement creates the container and reports the hostname back from inside it. Existing rows keep their stored names; the bound applies from the next launch, and a container orphaned by the old bug has to be removed by hand since it was never recorded as running. Separately, this work found that `bash` on Windows resolves to `C:\Windows\System32\bash.exe` — the WSL launcher, not a shell — which re-parses argv and rewrites paths on the way into the distro. Tests that execute generated shell through it do not fail honestly, they hang or report false positives (`shq`'s `$(whoami)` case came back *expanded*), so they now skip on win32 rather than being trusted or endured. That is a statement about the harness, not about the code: those scripts only ever run on Linux instances and in containers.

## D-43 — A sandbox learns its GitLab instance from the repos, not from a setting (2026-08-04)

**Context:** a sandbox came up green but its repo badge did not: `fatal: could not read Username for 'https://git.example.com': No such device or address`, an error that blames a credential prompt rather than the missing configuration behind it. The bootstrap already handles self-hosted GitLab — `GITLAB_HOST` extends token auth past gitlab.com — but nothing filled it in. `buildSpec` set `GITLAB_TOKEN` from the saved credential and stopped there, so `git config url."https://oauth2:$TOKEN@gitlab.com/".insteadOf` was the only rule written and a clone from `git.example.com` went out with no credential at all. Asking the user to set `GITLAB_HOST` by hand would have worked, but they had already said where the code lives — twice: in the repository URL, and in the credential's saved host.
**Decision:** derive it. `selfHostedGitLabHost()` reads the hosts out of the project's repo URLs (both `https://host/x` and `git@host:x` forms) and returns the single non-gitlab.com one; the credential's saved host is the tiebreaker for a project whose repositories are still shells, and repo URLs win over it because a credential is reused across projects while a repo belongs to this one. Repos spread across **two** instances resolve to null rather than a guess: `GITLAB_HOST` names one instance, and authenticating against the wrong one surfaces as a permissions error, which is a worse place to start debugging than an unset variable. It lives in `lib/git-host.ts`, free of Prisma, so it stays a pure function the tests import without standing up a database.
**Consequences:** verified end to end inside the running sandbox rather than only in the renderer — `git ls-remote` against the private repo fails with the reported error, then lists refs once the derived config is applied. Reading that bootstrap log to diagnose this turned up a separate leak worth more than the fix: `/var/log/nexus-bootstrap.log` (served by the UI's bootstrap-log route) contained the GitLab token, the Claude OAuth token and the project's own API secret in plaintext. The credential-config block was already careful to run untraced, but the `. /etc/profile.d/nexus-env.sh` **above** it was not — and xtrace echoes every `export` inside a sourced file, so sourcing it under trace dumps every project secret regardless of how careful the block below is. The trace now goes off before the source, in both places that do it, and a test walks the rendered script's `set -x`/`set +x` state to assert it stays that way. Any credential that reached an existing sandbox is in that log already and should be rotated.

## D-44 — A tailnet is named on the credential, and a sandbox with no key registers itself (2026-08-04)

**Context:** the Tailscale integration assumed Tailscale's own control plane. `tailscale up` was rendered without `--login-server`, so a sandbox joining a **self-hosted coordination server** — Headscale, or any other control plane a company runs itself and reaches at its own domain — went to `login.tailscale.com` no matter what key it was handed. The deeper problem is that the credential form asked for the one thing such a deployment usually cannot give you: pre-auth keys there are minted on the server (`headscale preauthkeys create`), or through an API key that is itself server-minted and global. The common shape is a tailnet where members authenticate through the company IdP and only the team operating the server has a console — so a user who reaches the tailnet every day has no console, no API key, and therefore no way to fill in the field the UI insisted on. Nothing about this is specific to one company's server; it follows from self-hosting the control plane at all.

**Decision:** the control server becomes a second, optional field on the **credential** rather than on the sandbox config — a coordination server is a property of the tailnet the key belongs to, not of one project, and pairing them keeps a key from ever being sent to the wrong control plane. Both halves are optional and at least one is required: a key alone means Tailscale's own, a server alone means a self-hosted one you cannot mint keys on. In that second case the sandbox bootstrap registers itself — `tailscale up` backgrounded, its output grepped for the URL it prints, echoed as `tailscale-auth-url=…` for the UI to pick up (`parseTailscaleAuthUrl`) — and a human approves it in the browser they are already signed in to. That fallback replaces the old keyless behaviour (install and WARN) everywhere, not just for self-hosted servers: the mechanism is identical against Tailscale's own control plane, and a printed URL beats a box with the daemon installed and nothing done with it.

**Consequences:** a **host** still refuses a keyless credential, and the check is explicit rather than implied. Its bootstrap is unattended and fatal on a failed join (D-34), so nobody is there to click the link; being told this at creation time is much better than a machine that provisions and then waits forever. No schema migration was needed — the credential's `data` blob is untyped, and `resolveTailscaleKey` still reads the legacy `token` field rows saved before this. Two things to know about the self-hosted path: nodes registered through OIDC are **not** ephemeral, so destroyed sandboxes linger in the node list until an admin removes them, and Tailscale SSH (`--ssh`, which the bootstrap always passes) depends on the server's policy allowing it — where it does not, the join fails and degrades to a WARN like any other. An ephemeral pre-auth key obtained from whoever runs the server avoids both, which is why the key field is still offered alongside the URL.

## D-45 — A sandbox's git token covers the ssh remote forms too (2026-08-04)

**Context:** `git clone git@git.example.com:acme/team/claude.git` inside a sandbox died with `Permission denied (publickey)`, on a box where `GITLAB_TOKEN` was set and the self-hosted host had been derived correctly (D-43). The token config was doing exactly what it said and nothing more: every `insteadOf` rule mapped the **https** prefix only, so an scp-style remote matched nothing, went out over real ssh, and authenticated as nobody — a sandbox has no ssh key for any git host and never will. The error names ssh rather than the missing rewrite, so it reads as a key problem on a machine that was never going to have a key, and the surrounding symptoms invite the wrong diagnosis (this one arrived alongside an unrelated tailnet question, as if the repo were behind the VPN — it is not, `git.example.com` resolves and answers publicly).

**Decision:** map all three remote forms per host — `https://host/`, `git@host:` and `ssh://git@host/` — onto the same token URL, through one `nexus_git_auth` helper that every provider calls instead of four hand-written `git config` lines. The scp form is not an edge case: it is what a GitLab or GitHub "clone with SSH" button hands you, what `.gitmodules` routinely carries, and what anyone pastes from a README — the form the user actually has is the one that has to work. The helper uses `--replace-all` for the first value and `--add` for the other two, so a re-bootstrap resets the list rather than appending a fourth duplicate.

**Consequences:** ssh remotes are now silently rewritten to token https for hosts we hold a token for, which is a hijack — and the right one here, since the alternative on these boxes is not "ssh with my own key" but "fails". It applies to `push` as well as `clone`, so an agent that commits over an ssh remote works without further setup. Verified against real git rather than by reading: with only the old rule an scp URL invokes `GIT_SSH_COMMAND`; with all three, all forms come out as `https://git.example.invalid/...`. Pre-existing and untouched: a *changed* token leaves the previous `url.…` section in `/etc/gitconfig`, since the token is part of the config key — harmless on a fresh sandbox, which is every sandbox.

## D-46 — A sandbox accepts its tailnet's routes, but not its DNS (2026-08-04)

**Context:** a sandbox that had joined the tailnet correctly still could not clone. The symptoms pointed everywhere except the cause: `git.example.com` resolved, answered on port 22, and refused the clone for want of an ssh key — while its **443 and 80 hung**, on a box where github.com, gitlab.com and api.civo.com were all reachable on 443, so it was not egress filtering. `tailscale status --json` had the answer: a peer advertised `203.0.113.153/32` — that git server's address — as a `PrimaryRoute`, and the sandbox's prefs read `RouteAll: false`. The `tailscale up` we generate never passed `--accept-routes`, so the node ignored the route and sent that traffic out its public gateway, where the internal HTTPS endpoint is not published. Every token-authenticated clone goes over https, so the one protocol the credential works on was the one that could not get there.

**Decision:** the sandbox join takes `--accept-routes`. Subnet routers are the mechanism by which a tailnet makes an internal service reachable, so a sandbox that joins a tailnet and ignores its routes has bought almost nothing — the address it gained is not what anyone joined for. `--accept-dns` deliberately stays **off**, which is not symmetry for its own sake: routes *add* reachability, while taking the tailnet's resolver *replaces* the sandbox's, and a tailnet that resolves public names poorly (or not at all) would break apt, npm, and every clone that was working before. The bigger blast radius loses.

**Consequences:** this is a network-posture default, applied to every sandbox rather than exposed as a toggle nobody asked for — but it is worth knowing what it can do: a tailnet advertising a route that covers a sandbox's *own* public address would blackhole the path Nexux reaches it by (ssh, terraform), and the sandbox would go unreachable while looking healthy. That is pathological tailnet configuration rather than a likely accident, and the same risk any tailnet member already accepts. It also settles D-45's residual worry: the ssh→https rewrite looked harmful on this host, since https was the dead port — with the route accepted, https is the *working* one and the rewrite is what makes the saved token do its job. Verified on the live sandbox before changing the template: `tailscale set --accept-routes` was the difference between a hung 443 and a working clone.

## D-47 — The bootstrap waits for a human, but only where the tailnet gates the clone (2026-08-04)

**Context:** a sandbox on a self-hosted tailnet came up with `repo` red and this in its log: `fatal: unable to access 'https://…': Failed to connect to git.example.com port 443 after 130444 ms`. Nothing was misconfigured — `/etc/gitconfig` had all six `insteadOf` rules (D-45), the node was on the tailnet, and `--accept-routes` (D-46) was in place; running `git ls-remote` on that same box afterwards returned refs in under a second. The bootstrap had simply reached the clone before anyone approved the registration link. That race is unwinnable by construction: an interactive (OIDC) registration needs a person, and the bootstrap prints the URL and carries on seconds later. The failure also lies about itself — a connect timeout reads as a network fault, not as "nobody has clicked the link yet".

**Decision:** the bootstrap blocks on the approval, and does so **only** for an interactive registration against a self-hosted control plane. That is the case where the tailnet is what makes the git host reachable at all; with an auth key `tailscale up` has already returned joined, and on Tailscale's own control plane a project's repos are not usually behind the tailnet — neither pays the cost. The wait is placed **late**, after every install that needs no tailnet and immediately before the git-identity lookup and the clones, so the human gets the whole install phase to approve and the wait is usually over before it starts. It re-announces the registration URL every 30s, because the UI reads a 400-line tail and the original announcement is long gone by then; and it polls `tailscale ip -4` rather than `tailscale status`, since a node can be up and still unregistered while only an address proves the join landed.

**Consequences:** it times out into a WARN rather than an abort — a machine with tooling and no checkout still beats no machine — and the WARN says what to do. The loop runs with tracing **off**, which is not about secrecy: traced, it writes several lines per poll for up to ten minutes and would push its own re-announced link back out of the tail it was re-announced into, defeating the point. Verified by executing the rendered loop against a stubbed `tailscale`, in both outcomes (approved on the third poll → "approved after 10s", never approved → WARN, exit 0) — the first attempt at that harness passed for the wrong reason, since a counter incremented inside `$( )` lives in a subshell and never advanced. Unaddressed on purpose: an existing sandbox that lost this race still has to be recreated, since nothing re-runs the repo section (a "Retry setup" action was offered and declined in favour of recreating).

## D-48 — Setup is retryable, and a retry adopts what it finds (2026-08-04)

**Context:** the approval wait (D-47) narrowed the race but could not remove it — a run that night timed out after its full 10 minutes and the registration landed **44 seconds later**, by which point the clone had already spent 131s on a TCP timeout and the bootstrap had written its completion marker. The machine was seconds away from being fully usable and nothing could act on that: the only recovery was destroying it and provisioning again, which costs a fresh 15 minutes and re-runs the same race against the same clock. The failing half is also a small and well-bounded one — clone, install, build — while everything expensive (apt, Docker, Node, Claude Code, the CLIs) had already succeeded.

**Decision:** the repo half of the bootstrap becomes a named, re-runnable unit. `renderRepoSetup` is extracted from `renderCloudInit` and **shared** with a `retry-setup` route, so there is exactly one definition of what "set up" means rather than a bootstrap version and a repair version that drift. Re-running it is safe by construction: `renderRepoSection` now checks for `<dir>/.git` and **adopts** an existing checkout instead of re-cloning, because re-cloning means deleting a tree that may hold work — an expensive mistake weighed against a merely redundant clone. Install and build still re-run on an adopted checkout, since that is usually the half that failed. The block carries its own `git config` rules along, so a retry on a box whose `/etc/gitconfig` is stale repairs itself rather than failing the same way twice.

**Consequences:** the route refuses early where it can, and the important refusal is a sandbox whose project is on a self-hosted tailnet that this node has not joined yet: every unreachable repo costs ~130s before git gives up, so attempting it would spend minutes to reproduce the original failure and report it as a network fault. It says "approve the registration first" instead, naming the actual next step. Extracting the renderer broke the file mid-edit and the repair was done with `sed` on exact line ranges rather than by retyping ~60 lines of shell — the tests were what confirmed the extraction was behaviour-preserving, and they also caught a real regression introduced along the way: building the clone chain eagerly called `shq(null)` for a mounted repo that was never going to be cloned. Still not addressed: nothing *notices* a pending approval on your behalf — Telegram notification was proposed and not taken.

## D-49 — ClickUp connects via OAuth, with the app credentials pasted once into Settings (2026-08-04)

**Context:** ClickUp offers two ways in: a per-user personal API token (the GitHub-PAT shape) and an OAuth2 authorization-code flow. The goal was "connecting an account is one click", which the PAT shape cannot give — every account means another trip to ClickUp's settings to mint a token. But OAuth needs a client id/secret, and Nexux is local-first: there is no hosted backend to own a shared ClickUp app, so *someone* must create one.

**Decision:** OAuth, with the app creation paid once instead of per account. The operator creates a ClickUp OAuth app (the dialog shows the exact redirect URL to register, derived from the browsing origin) and pastes its client id/secret into Settings (`clickup_client_id`/`clickup_client_secret` — the Telegram precedent, not env vars, so setup stays in the UI). After that, every connect — including reconnects and additional accounts — is a single click. Tokens land in the pre-built `ConnectedAccount`+`OAuthToken` tables; the unused `OAuthState` table finally earns its keep as the CSRF nonce store (single-use, 10-minute expiry, pruned on each new flow). ClickUp's token exchange takes no `redirect_uri` and no PKCE, so `codeVerifier` stays null. The callback never renders JSON: success and every failure (forged/expired state, user cancel, exchange error) redirect back to `/settings?tab=integrations` with a query param the ClickUp card turns into a toast — a browser mid-flow should always land somewhere navigable.

**Consequences:** accounts de-dupe by ClickUp user id in `metadata`, so reconnecting refreshes the token instead of stacking rows. `redirect_uri` derives from the request origin, so the URL registered on the ClickUp app must match the origin the user browses from (localhost:3000 vs :3030 in Tauri — register both, or connect from one). Access tokens are stored plaintext like every other secret in the SQLite file (known repo-wide condition); ClickUp tokens currently do not expire, so there is no refresh machinery — `expiresAt`/`refreshToken` columns are ready if that changes. `ConnectedAccount` has no `workspaceId`, so ClickUp accounts are global like GitHub ones.

## D-50 — ClickUp lists map to phases, tasks to features, through a cache and a review step (2026-08-05)

**Context:** with a ClickUp account connected (D-49), the goal was making features and phases cheap to create from work that already lives in ClickUp. Three mapping questions had no obvious answer: what becomes a `DevPhase`, what to do with ClickUp's free-form statuses, and whether to import live from the API or through a local cache.

**Decision:** a ClickUp **list** maps to a `DevPhase` (people already name lists "Sprint 1"/"MVP"; folders are carried only as a label), and its **tasks** map to `Feature`s — but never blindly: the import dialog is a review tree in the `generate-roadmap-dialog` mold, every task individually checkable and editable, phase creation optional. Statuses map by ClickUp's stable `statusType`, not the free-form label (open→backlog, custom→todo, done/closed→done), with the original label shown beside the mapped one in review; closed work defaults to unchecked. Tasks flow through a `ClickUpTask` cache table + `FeatureClickUpTask` join — a deliberate mirror of `GitHubIssue`/`FeatureIssue`, so search/filter never costs a network call and every imported feature keeps a provenance link. The write path is one transaction copied from `/roadmap/apply`, except imported features keep their mapped status (roadmap forces backlog), so ordering is computed per kanban column.

**Consequences:** an import is repeatable — one list per round, run it again for the next list. Sync is upsert-only (like GitHub's): tasks deleted in ClickUp linger in the cache until noticed. Nothing writes back to ClickUp yet; that (close task on done, PR link comments) is the designed-but-deferred third step. The base-ui `SelectValue` renders raw values unless given a label resolver — fixed in the ClickUp selects, and the same latent bug exists in the GitHub issue picker.

## D-51 — A GitHub board's iterations are phases, its columns are status, and sync only moves (2026-08-05)

**Context:** GitHub Projects V2 has more structure than raw issues — Status columns, iteration sprints, custom fields — but only via GraphQL and only with the `project` scope (the token link pre-selects it since 2026-08-05). Two mapping questions: what becomes a phase, and what re-sync is allowed to do.

**Decision:** **iterations → DevPhases** (that's what sprints are), **Status columns → kanban status** — columns are workflow position, not grouping, so mapping them to phases would have been wrong; free-form column names map by heuristic on the stable words (progress/review/done/todo), with the original name shown beside the mapped one in review. Items keep the per-item checkbox rule from the ClickUp import; drafts import without provenance; PR items are skipped (code, not work). The Nexux project ↔ board link persists as a Settings key (`github_project_link:<projectId>`, JSON), and **re-sync is movement-only**: it updates status and reassigns to an *existing* phase matching the iteration's name, but never creates features or phases — import is the single path that adds work, so a renamed iteration can't silently spawn a duplicate phase tree.

**Consequences:** re-sync is one-directional (GitHub → Nexux); moving a card on the Nexux kanban does not touch the board. Items whose iteration matches no phase keep their current phase. Tokens minted before the `project` scope fail the GraphQL calls — the error message says to regenerate. `mapColumnToStatus` is duplicated client-side so the review can show the mapping before anything is sent; the service copy is the one tests pin.

## D-52 — Board discovery is three independent sources plus a URL escape hatch (2026-08-05)

**Context:** D-51 listed boards from `viewer.projectsV2` + `viewer.organizations.projectsV2`, with the org half in a separate query so a token without `read:org` wouldn't take the user's own boards down. In practice that degraded to *only* the user's own boards: a live token with `project, read:user, repo` saw 1 board while its owner had ~15. The GitHub behaviour behind it is not what the code assumed — `organization(...)` resolves fine without `read:org`; what fails is **selecting a scope-gated field on it** (`login`, `id`, `name`). And `viewer.organizations` doesn't error when you select nothing gated, it returns an empty list — so the failure was silent, not caught.

**Decision:** Discovery is three sources, queried independently, each degrading to `[]` on its own error: (1) `viewer.projectsV2`; (2) org boards — logins from REST `/user/orgs` (which lists public memberships without `read:org`), then one aliased GraphQL query per login selecting **no** gated field, the owner taken from the login we asked for rather than the response; (3) boards linked to repos the account can reach (`viewer.repositories` with OWNER/COLLABORATOR/ORGANIZATION_MEMBER), the only listing that surfaces someone else's board. Results dedupe by node id, first source wins. What no listing can reach — another user's board, an org whose membership is private — gets an escape hatch instead of a bigger query: `resolveProjectV2` takes a pasted URL (`/orgs|users/<login>/projects/<n>`, `/views/…` tail tolerated) or the `owner/n` shorthand, and asks for both owner types in one query since the wrong one comes back as a NOT_FOUND error beside usable partial data. Finally, a token whose `x-oauth-scopes` lacks `read:org` says so in the dialog; a fine-grained token sends no such header, and unknown scopes claim nothing.

**Consequences:** the same unchanged token now lists 15 boards. Coverage of orgs is still bounded — private-membership orgs need `read:org` or the URL paste, org logins cap at 20 and the repo scan at the 100 most recently pushed repos. A board's `owner` is a display label from the source that found it (org login, or the repo's owner), not necessarily the board's real owner — nothing keys on it. Boards resolved by URL live in dialog state, so they vanish on reload unless imported (the import writes the `github_project_link` Settings key, which is what re-sync reads).

## D-53 — Any URL handed to a third party comes from NEXUX_WEB_ORIGIN, never from the request (2026-08-05)

**Context:** ClickUp OAuth could not be completed on a Nexus host and looked like a Tailscale problem. It wasn't. Next's standalone server builds request URLs from the address it *bound to*, not from the `Host` header, so inside the Docker image (`HOSTNAME=0.0.0.0`) `req.nextUrl.origin` is `http://0.0.0.0:3030` on every request — a spoofed `Host` and even `X-Forwarded-Host` do not change it (only `X-Forwarded-Proto` gets through). `/oauth/start` built `redirect_uri` from it, so ClickUp was asked to match `http://0.0.0.0:3030/api/clickup/oauth/callback`. Meanwhile the Settings card quoted `window.location.origin` — the *browser's* view, `http://100.x.y.z:3030` — as the URL to register. The two could never agree, and the operator had no way to see why: the value the server sent was never displayed anywhere.

**Decision:** A new `publicOrigin(req)` (`apps/web/src/lib/public-origin.ts`) is the single source for outward-facing URLs, resolving `NEXUX_WEB_ORIGIN` → `X-Forwarded-Host`/`-Proto` → `Host` → `req.nextUrl.origin`. `NEXUX_WEB_ORIGIN` wins because it already means "the URL you actually open the dashboard on" (it is the terminal server's CORS origin, and `template-host.ts` already sets it to the Tailscale URL when provisioning a host) — the deployment had the right answer on hand and the code simply wasn't asking. The fallback chain keeps `pnpm dev` working unchanged. `GET /api/clickup/config` now returns `callbackUrl` from the same helper and Settings displays *that*, so the URL you are told to register is by construction the one ClickUp will be asked to match.

**Consequences:** an install reachable on something other than its bind address must set `NEXUX_WEB_ORIGIN` — already true for the terminal, now true for OAuth too, and a wrong value is visible in the Settings card instead of silent. The trailing slash is stripped, and comma-joined `X-Forwarded-*` chains use the client-facing hop. This was the only place a request-derived origin escaped to a third party; the remaining `new URL(req.url)` calls only read query params. A private-network install still depends on the provider accepting a private-IP `http://` redirect URL — where it does not, point `NEXUX_WEB_ORIGIN` at a `tailscale serve` HTTPS hostname (`https://<node>.<tailnet>.ts.net`), which needs no code change.

## D-54 — Every level of the ClickUp picker is a live call, including workspaces (2026-08-05)

**Context:** A freshly connected account on a Nexus host showed a healthy green card — username and email correctly read from `/user` — and an import dialog whose **workspace** dropdown was empty, so nothing below it could ever load. `fetchIdentity` reads `/team` behind `.catch(() => [])` ("non-fatal if it fails, the token is what matters"), and D-50 had made that stored `metadata.teams` the picker's source. The token was never the problem: probing the live install, `/spaces?teamId=…` returned all four spaces with that same stored token, and a `revalidate` re-ran `fetchIdentity` and populated `teams` on the first try. `/team` had failed exactly once, at connect, and `[]` was persisted as fact — permanently, since nothing re-reads it unless a human happens to press Revalidate. The cure existed and was undiscoverable: no error, no log, no empty-state text, and an empty `<Select>` reads as "this account has no workspaces".

**Decision:** Workspaces are a live endpoint, `GET /api/clickup/accounts/[id]/teams` (`listTeams`), matching the spaces and lists below them — the cascade is now uniform, and a transient ClickUp failure costs a retry rather than the account. `metadata.teams` survives only as the label in the Settings card. The `.catch` stays (connecting must not fail over a workspace list) but logs, because the silence is what made this undiagnosable from the outside. `ClickUpTeam` became a type alias: it lands in Prisma's `metadata`, and `InputJsonValue` rejects interfaces, which carry no index signature.

**Consequences:** the picker costs one extra request per account selection, cached by React Query for the dialog's lifetime. A failing `/team` now surfaces as a 500 on the dropdown instead of a silent empty list — visibly broken beats invisibly broken, and it is the same failure either way. This reverses the "not a live call" half of D-50; the rest of that decision stands. Accounts already stored with `teams: []` need no migration — nothing reads that field for the picker any more.

## D-55 — The terminal bounds its own ssh connect, and narrates the wait (2026-08-06)

**Context:** Terminals on remote machines appeared broken while local shells worked. The instance was neither down nor throttled — a `t3.medium` still finishing its bootstrap sat at a load average near 20 on 2 vCPU (`vmstat` reported steal 0, ruling out a t3 credit cliff), and a CPU-starved sshd completes the TCP handshake and then misses the SSH banner window. OpenSSH waits **120 seconds** for that banner by default (documented, not measured here — every reproduction run carried a timeout of its own), so the pane showed nothing before dumping ssh's own error. Every other ssh caller in the repo (`execRemote`, ×3 in `@nexux/sandbox/remote.ts`) had passed `ConnectTimeout=15` since it was written; the terminal was the one that had not.

**Decision:** `sshLaunchArgs` is an exported pure function owning the flags: `ConnectTimeout=15` — chosen because OpenSSH applies it to the banner exchange as well as the TCP connect, which is the failure that actually occurs, and matching `execRemote` rather than inventing a second number — plus `ServerAliveInterval=15`/`ServerAliveCountMax=3` so a session that dies mid-flight (instance stopped, laptop off the tailnet) drops in ~45s instead of waiting out TCP. `BatchMode` is deliberately **not** set: this is an interactive pane, and a password prompt is a legitimate outcome for a target Nexux did not provision. Pure because the cases worth testing are hosts that never answer, which no test should depend on reaching.

**Consequences:** a wedged remote fails in 15 seconds with a line naming it, and the pane announces `[connecting to <target>…]` on the way in so the wait reads as a wait. A genuinely slow first connect over a congested tailnet now has 15 seconds rather than 120 — the trade is deliberate, since a retry is one click and a two-minute blank pane is indistinguishable from a bug. Timeouts live in the terminal server, not the UI: the pty is the only place that knows whether a session ever opened.

## D-58 — Templates are an export shape, not a new entity (2026-08-07)

**Context:** Team hand-off needs three things the export system almost had: sandbox settings visibly travelling (they always did — `SandboxConfig` is Layer 1 — but the import plan never counted them, so the preview read as if they were dropped), exporting a chosen subset of projects (the backend's `scope` supported it since spec 18; the UI hardcoded `all`), and a "start from here" file for a teammate that doesn't drag along one person's features, documents and chat history.

**Decision:** No `Template` model. A template is `?template=true` on the same export: structure travels (repositories, stack, sandbox config, brain, agent/skill joins, env var *keys*), work product does not (features, dev/definition phases, documents, schedules, conversations), and secrets are refused outright — the route 400s on `template && includeSecrets`, because the file exists to be handed to someone else. `meta.template` is an optional field, so `EXPORT_VERSION` stays 1 and an old install just sees a smaller ordinary export. Import needs no new code path: fewer sections, same apply. The machine-state line of D-31 (spec 18's three layers) is untouched — running `Sandbox` rows still never travel; the fix for "sandboxes aren't exported" was counting `sandboxConfig` in the plan so the preview *shows* it. UI: project-scope switches with per-project selection in Settings, plus an Export button on the project page whose dialog defaults to template.

**Consequences:** Sharing a project is: Export on the project page → send the JSON → teammate imports from Settings. What a template deliberately loses: progress. What it deliberately keeps: credential *shells* and env var keys, so the destination gets a checklist of what to fill rather than a config with holes. A saved-in-app template library (create-from-template in the wizard) remains open; if it ever lands, this export shape is its interchange format.

## D-57 — The sidecar is the native app's only bridge to the machine (2026-08-07)

**Context:** Two gaps surfaced the day the first full release shipped. External links did nothing in the native app — the Tauri webview silently swallows `target="_blank"` (it never creates windows), and the web UI deliberately carries no Tauri JS API, so every `<a target="_blank">` in the app was dead there while fine in a browser. And the update badge could see a new release but only link to its page; knock's one-click installer runs `curl | bash` in a Terminal via a Tauri command, which Nexux can't copy directly — no Tauri API in the UI, and a private repo where raw-URL install scripts can't even fetch the assets.

**Decision:** Both go through the sidecar, which already runs locally as the user: `POST /api/open-url` hands an http(s) URL to the OS opener, and `POST /api/updates/install` downloads the platform asset (GitHub API with the saved token — works private, via the asset URL + `Accept: octet-stream`) and installs it in-process — knock's install-app.sh mechanics ported to node: DMG mount → replace /Applications → `xattr -dr com.apple.quarantine` (no sudo; the copy is ours), NSIS exe launched detached on Windows, AppImage into `~/.local/bin` on Linux. Both routes are gated by `NEXUX_NATIVE=1`, set only by the sidecar's start.js — a host or dev install answers 404 and the client falls back (window.open / release link). Client-side, one capture-phase document listener reroutes every `target="_blank"` anchor through open-url when `/api/version` says `native`, fixing all existing and future external links without touching each one.

**Consequences:** The native updater is one click: badge → download → install → "restart to finish". deb/rpm stay manual (they need root; the AppImage path doesn't). URL validation on open-url is strict http(s) — the endpoint is reachable by anything that can reach the sidecar port, and the OS opener would happily take `file:`. The document listener means `window.open` calls from JS (not anchors) still die silently in the webview — none exist today; new code should use `openExternal` from `services/updates`.

## D-56 — The release tag is the version; manifests sync from it (2026-08-06)

**Context:** Shipping a native release required bumping the version in five files (three package.json, tauri.conf.json, Cargo.toml) and release-native.yml *failed the build* if the tag disagreed with tauri.conf.json — a forgotten bump cost a full CI round-trip. Meanwhile nothing in the UI said what build was running: `/api/version` existed (Docker env only) but had no consumer outside Settings → Nexus hosts, and the native app had no build identity at all. knock (same author) had already solved both: a `set-version.sh` that edits every manifest, CI that syncs from the tag instead of checking against it, and a statusbar showing version + commit with an update badge.

**Decision:** Copy knock's model, adapted to the sidecar architecture. The tag is the single source of truth: `scripts/set-version.sh` bumps all five manifests (+ Cargo.lock) in one command, and the build job runs it from `GITHUB_REF_NAME` before building, so the check step is deleted rather than kept alongside — a check and a sync answer the same question and the sync also fixes it. Build identity travels one env contract (`NEXUX_VERSION`/`NEXUX_GIT_SHA`/`NEXUX_BUILT_AT`) with three feeders per runtime: Docker ENV (unchanged), `build-info.json` baked by build-sidecar and loaded by start.js (a GUI app has no other channel into the sidecar's env), `git rev-parse` for dev. The UI reads only `/api/version` and `/api/updates` — no Tauri command, so browser and native share one statusbar, unlike knock's `invoke()`-based one. The update check lives server-side with a 30-minute cache (one GitHub call shared across tabs), answers 204 when no release is published (a fresh install's normal state must not error the console), and serves stale cache over a GitHub error.

**Consequences:** Releasing is `scripts/set-version.sh X.Y.Z && git commit && git tag vX.Y.Z && git push origin main vX.Y.Z` — and even skipping the script cannot mis-version the build, because CI re-syncs from the tag. The parity test (all five versions agree) still guards local drift. The update badge only ever points at the release page; there is no in-app installer (knock has one) — the download-and-run step stays manual until install scripts exist. Drafts don't count as releases: publishing the draft that release-native.yml creates is the act that makes every running install light up "update available".

## D-59 — A feature's PR flag is nullable, so "inherit" is a state (2026-08-10)

**Context:** Whether a sandbox run ends in a pull request was one project-wide switch, `SandboxConfig.createPr`. That is the right default but the wrong granularity: a throwaway spike and a shippable feature go through the same queue, and the only way to run one without a PR was to flip the project setting and remember to flip it back. The obvious fix — a boolean on `Feature` defaulting to the project's current value — quietly breaks the default: every feature would be stamped with whatever the project said at creation time, so changing the project setting later would move nothing, and the setting would decay into a template for new features.

**Decision:** `Feature.createPr` is `Boolean?`, with NULL meaning "inherit" as a first-class third state rather than an unset boolean. Inheriting features keep reading `SandboxConfig.createPr` at dispatch and move whenever it moves; only an explicit true/false pins one feature. The override is applied by `withFeaturePrOverride` in `agent-core.ts` — a pure function over `AgentPolicy` — called from `createTask` right before the policy reaches the runner, which is the one place every dispatch path already converges (board queue, Telegram, the tasks API, and follow-ups resuming a branch). The UI never exposes the nullable boolean: `FEATURE_PR_MODES` (`inherit` / `always` / `never`) plus a pair of total mapping functions keeps the tri-state honest at the edges.

**Consequences:** Existing features needed no backfill — the column is NULL and they behave exactly as before. A follow-up task inherits the parent's decision through the same `featureId`, so a chain of runs on one feature cannot change its mind halfway. The cost is that "does this feature open a PR?" has no single answer without knowing the project default; the drawer's helper line names where the default lives instead of fetching it, since the feature dialogs open constantly and the project setup endpoint is heavy. The flag governs only the PR step — a `never` feature still branches, commits and pushes.

## D-60 — The dev server's memory is Turbopack's, and NODE_OPTIONS has to be declared to reach it (2026-08-12)

**Context:** Agent tasks kept dying six minutes in with "Interrupted by a server restart". The dev server was restarting every few minutes — `⚠ Server is approaching the used memory threshold, restarting...` — and each restart killed the in-flight task. Raising `--max-old-space-size` changed nothing, which sent the investigation down two wrong paths (an unbounded `ws.send` queue in the terminal server, then a suspected reconnect loop). Both were dead ends, and RSS was the reason: it hovered between 4 and 8 GB and never matched the threshold Next was tripping.

**Decision:** Turborepo hands tasks a *filtered* environment, so `NODE_OPTIONS` was being dropped before `next dev` ever saw it — the ceiling appeared to be set and was discarded one layer above the process that needed it. `globalPassThroughEnv: ["NODE_OPTIONS"]` in `turbo.json` fixes that; Next's own rule is `used_heap_size > 0.8 * heap_size_limit` (`start-server.js`), so on the default ~4.3 GB heap it restarts at ~3.4 GB, which is why the restarts arrived every few minutes and killed the in-flight task each time.

**Where the memory goes, measured.** Live heap after `HeapProfiler.collectGarbage`, via CDP against the running server:

| Workload | Growth |
|---|---|
| Idle, no browser attached | **0** (flat at 93 MB heap / 584 MB RSS) |
| 800 server-side page renders / 150s | +138 MB |
| 800 RSC-header requests / 150s | +190 MB |
| 60 mtime touches + renders / 120s | +12 MB |
| 40 real source edits (recompiles) / 120s | +10 MB |
| **A real browser session on the dashboard, 290 requests / 180s** | **+2344 MB** |

Nothing synthetic reproduces the last row — it is an order of magnitude above a load four times heavier in requests. So the app's own request handling is *not* the leak, and neither is HMR recompilation, which was the obvious suspect and measures at 10 MB. What is left is the live client: the HMR socket, the dev overlay, streaming flight responses. That part is unproven; reproducing it needs a real browser attached, which no `curl` loop stands in for.

It is also not the bundler. A clean A/B with identical load and duration puts Turbopack at +138 MB and webpack at +819 MB, so Turbopack is the *better* of the two here. The earlier 1953-vs-1 MB figure that said otherwise compared a browser-driven Turbopack run against a webpack run in which every route was 500ing, and is worthless.

**Consequences:** Most of the process's RSS is Turbopack's native (Rust) memory, which V8 does not count — a box apparently using 8 GB can still be restarting over a 3.4 GB heap. Any memory work here must measure live heap after `HeapProfiler.collectGarbage` under a *fixed* workload; RSS misled this investigation twice, and an unmatched A/B misled it a third time. The cheapest mitigation is not leaving the dashboard open during a long agent task. Bun is not an escape hatch: `packages/db` uses `@prisma/adapter-better-sqlite3` and better-sqlite3 is unsupported (oven-sh/bun#4290), so the app boots and every query fails. `--webpack` now at least runs (see the instrumentation split below) but is not worth switching to. The backpressure added to the terminal server on the way through stays: an unbounded send queue is a real bug, just not this one.

## D-61 — Node-only startup work lives in its own module, not behind an early return (2026-08-12)

**Context:** `instrumentation.ts` guarded its body with `if (process.env.NEXT_RUNTIME !== "nodejs") return;` and then reached ptys, Prisma and the filesystem through dynamic imports. That stops the code from *running* on the edge runtime but not from being *bundled* for it: webpack still has to resolve every import behind the guard, and dies on `dev-console.ts`'s `fs/promises`. Turbopack happened to tolerate it, so the incompatibility sat unnoticed until a `--webpack` run was needed to measure something else — where it surfaced as every route returning 500, which reads as a broken app rather than a bundling problem.

**Decision:** The work moved to `instrumentation-node.ts`, reached from a single guarded dynamic import (`if (NEXT_RUNTIME === "nodejs") await import("./instrumentation-node")`). That is the shape Next documents, and it is the one a bundler can act on: the whole module drops out of the edge build instead of having to resolve.

**Consequences:** Both bundlers now start the app cleanly, so `--webpack` is available as a comparison point rather than a broken path — which is what allowed the A/B in D-60 to be run honestly at all. Anything node-only added to startup belongs in `instrumentation-node.ts`; putting it back in `instrumentation.ts` re-breaks the edge build, and only under webpack, which is the slowest possible way to find out.

## D-62 — The MCP control surface: scoped tokens, and a tool layer that cannot reach past its context (2026-08-13)

**Context:** Driving Nexux from outside the dashboard — sending a task from a local Claude, asking what a run is doing when nothing has come back over Telegram, hooking another system in — needs an inbound programmatic path, and the app had never had one. Telegram is outbound only, there is no middleware, no session, no auth of any kind (D-01: local-first, no multi-user auth). So the first question was not "which tools" but "what is a token allowed to do", because one of the obvious tools provisions a Civo/AWS instance and spends money.

**Decision:** Three separate calls, each of which could reasonably have gone the other way.

*Tokens are hashed, scoped and revocable by timestamp.* `ApiToken` stores only the sha-256 of a `nxs_`-prefixed 32-byte random value; the token is shown once at creation and is unrecoverable afterwards, which makes "someone shared their screen" a non-event for tokens issued earlier. Unsalted and un-stretched on purpose: this is a 256-bit random value, not a human-chosen password, so there is no dictionary to defend against and a per-row salt would only prevent the unique-index lookup that makes verification one query. Unknown, malformed and revoked tokens all get the same bare 401 — distinguishing them tells a prober which half they got right. Revocation is a timestamp rather than a delete, because after discovering a leak, when a token was created and last used is exactly what you want to keep.

*Scopes are split by blast radius, not by route.* `sandboxes:write` is separate from `tasks:write` specifically so a token handed to an external system can dispatch work onto machines that already exist without being able to buy new ones. Scopes that cannot be parsed grant nothing rather than defaulting to open.

*The tool layer lives in `@nexux/mcp` behind a `NexuxContext` the host implements,* and imports nothing but node builtins — no Prisma, no Next, no third-party dependency. That is what lets the same definitions serve the in-process `/api/mcp` route now and a published stdio binary later, and it is also what makes the scope check mean anything: a tool that could reach the Prisma client could reach every table whatever its scope said. Each tool carries its own scope in its definition rather than being looked up in a side table — a table is something a new tool can be forgotten from, and a forgotten tool would have to fail either closed (silently unusable) or open (silently unguarded).

**Consequences:** An out-of-scope tool answers exactly as an unknown one does, and `tools/list` is filtered too: advertising a tool that will always be refused invites a client to keep trying it and tells the holder of a narrow token what a broader one could do. The transport is stateless — no `sessionIdGenerator`, so every request re-verifies the token instead of trading it for a session. That costs a database lookup per call and buys the property revocation exists for, which is asserted by a test rather than assumed.

An MCP request carries a token, not a cookie, so there is no active workspace to read — `getActiveWorkspaceId()` reads `next/headers` and would throw. Tokens are install-wide, so the surface answers for the default workspace, and the boundary is enforced by id as well as by list: filtering lists alone would leave another workspace's task readable by anyone who guessed its id. Per-workspace and per-project tokens stay open questions in spec 21.

The scope list now exists twice — the package cannot import the app, and the app should not import a package to render a settings checkbox — with a test in `apps/web` asserting the two agree, so they cannot drift into minting tokens for scopes no tool honours. Failures from the host come back as tool results flagged `isError` rather than protocol errors, so "that sandbox is already running a task" is something the model reads and adapts to. `nexux_create_task` calls `createTask` rather than reimplementing dispatch, so it inherits the invariants D-59 put there and cannot become a fifth path that drifts.

Answering a blocked run is deliberately *not* in the surface. `nexux_activity` reports blocked runs, but `needsInput` is a dev-console concept — a property of an interactive session, not of a pipeline task — and delivering an out-of-band answer into one raises session ownership and racing-answer questions that are a design problem, not a wrapper. It gets its own spec.

## D-63 — The self-update collects the image it replaces, and names the disk when the disk is the problem (2026-08-16)

**Context:** A host at 100% disk failed its update with `no space left on device` while extracting a layer, and the log said `FAILED: could not pull — check the registry credentials`. The credentials were fine. The host had 23 images totalling 30.58GB, of which 22.75GB was reclaimable: every update pulls a new image and nothing on the host ever collected the one it superseded, so a host that has updated a dozen times fills a 39GB volume and then cannot update again — the failure mode arrives precisely when you most need the update to work.

**Decision:** `update.sh` runs `docker image prune -f` before the pull, and both the updater and the initial provisioning branch on `df` when a pull fails, reporting a full disk as a full disk. The prune is `-f`, never `-af`: `-a` would drop the image the running stack was started from, so a restart would have to re-pull. Volumes are never candidates — they carry the database, the credentials and the search indexes.

**Consequences:** A host now reclaims its own space on the schedule it creates it, so the disk no longer ratchets upward with each update. The two failure messages have diverged, which is the point: "the disk is full" and "check the registry credentials" send an operator to different places, and the old message sent them to rotate a token that was never wrong. A host already at 100% still needs one manual `docker image prune -af` before it can pull the update that contains this fix — the fix ships inside the image it cannot yet fetch.

## D-64 — Delivery sweeps the workspace for the task branch, instead of trusting workDir (2026-08-17)

**Context:** A feature pinned "pull request: always" ended with no MR and no error anyone could act on. The task ran at the project's main repo (`acme-api`), but the change was frontend: the agent created the branch in the sibling checkout `acme-ui`, committed there, and said so in its report. The pipeline counts commits only in workDir, read 0, and completed with "the agent made no commits — nothing to open a PR with", never reaching its own push/PR phase. A follow-up asking for the MR cannot escape either: the follow-up prompt forbids the agent from pushing or touching PRs (Nexux owns delivery), so that run also ends with zero new commits and the same early-return fires before the phase that knows how to create the missing PR. Two parties each correctly refusing their half left nobody delivering.

**Decision:** After the agent run, when `createPr` is on, a sweep (`deliverySweepCommand`/`parseDeliverySweep` in `agent-core.ts`, pure and tested) scans every checkout in the workspace parent (`../*/` from workDir) for the task branch carrying commits absent from every remote (`rev-list --not --remotes`), skipping checkouts with no origin. Delivery then runs per target: push, then create the PR/MR — or comment on the existing one when `prUrlMatchesRepo` says this checkout is the PR's own repo (slash-bounded path-prefix match on the normalized origin, so `owner/app` cannot claim `owner/app-ui`'s PRs). workDir still joins the list when this run committed there even with nothing left unpushed, because an agent that pushed by itself still leaves the PR itself owed. GitHub-vs-GitLab is decided per target's own origin, not the workDir repo's. The task row keeps one `prUrl` (the pre-existing one, else the first opened); further URLs are appended to the report and the log.

**Consequences:** Work landing in a sibling repo, a `createPr` flipped on after the run, and a previously failed push all deliver on the next run instead of dying as "no commits". The zero-commit completion now means the sweep found nothing anywhere — which is what that message always claimed to mean. A cross-repo feature can open one PR per repo under a single task; the row's single `prUrl` column is a known flattening (extras live in the report). Branch identity across checkouts is trusted on purpose: the slug carries a per-task suffix, so collisions between unrelated tasks are not a practical concern. The stranded MR that exposed this was rescued by hand (pushed from the sandbox, `glab mr create` → acme-ui!280, rows backfilled).

## D-65 — Feature planning runs lock-free on the dev sandbox, because plan mode cannot write (2026-08-19)

**Context:** Features needed real implementation plans — grounded in the actual checkouts, not the embeddings index — without interrupting whatever the dev sandbox is already running. The dev queue is serial by design (`acquireSandboxLock`): two agents mutating one working tree would fight. That serialization is protecting the *write* path, though, and a planning run has no write path.

**Decision:** A plan run is a Claude plan-mode invocation (`--permission-mode plan`, threaded through `buildClaudeCommand`) — the CLI itself refuses edits and mutating commands, so read-only is enforced by the tool, not by prompt courtesy. It therefore skips the sandbox lock and the dev queue entirely, never resumes the chat's `devSessionId` (fresh session every time), and is capped at one per sandbox purely as a resource cap. Always Claude regardless of the project brain — OpenCode has no read-only equivalent. The reply text is the deliverable, saved into the **`Plan` model, which existed dormant** (zero usages) with exactly the right shape: `featureId`, `content`, `draft → approved/rejected`. `buildFeaturePrompt` hands the newest non-rejected plan to the implementing run, so a rejected plan cannot steer the implementation. New `kind: "plan"` on `SandboxTask` reuses the log/cost/Telegram/Runs-list plumbing for free.

**Consequences:** Planning is delegable to the sandbox mid-work: the plan lands as a reviewable draft on the feature (board chip, dialog section with approve/reject), and dispatching the feature later carries the plan into the agent's prompt. A crashed server settles orphaned plan runs at boot (`recoverPlanRuns`) — there is no queue to resume, settling is the whole recovery. Cost of the choice: a plan run shares the VM's CPU/RAM with live work, and a headless plan-mode run must end its reply with the full plan (the prompt demands it) since the plan text is all Nexux keeps.

## D-66 — A GitLab server is a row with a URL, and its token is usually one you already saved (2026-08-27)

**Context:** GitHub and ClickUp each have exactly one API host, so both services hardcode theirs and an "account" needs no address. GitLab breaks that: `gitlab.com` and a company's `gitlab.acme.dev` are the same product over different data, teams routinely have both, and the self-hosted one is where the work actually is. Meanwhile the install already holds GitLab tokens — `CloudCredential` rows with `provider: "gitlab"` that clone repos and log in to `registry.gitlab.com` — carrying the very `api`/`read_api` scope reading issues needs. Copying GitHub's shape verbatim would have hardcoded a host that is wrong for most users and demanded a second token for the same permissions.

**Decision:** A GitLab server is a `ConnectedAccount` (`providerType: "gitlab"`, `authMode: "pat"`) whose `metadata.baseUrl` is the instance origin every API URL is built from — adding a second instance is adding a second row, and identity is (instance, username) so one login on two servers is two servers, not a duplicate. The token resolves credential-first: `metadata.credentialId` names a saved GitLab `CloudCredential` and `getGitLabAuth` reads the live token out of it; a pasted PAT is the fallback and lands in `OAuthToken` the way GitHub's does. Switching a server onto a credential deletes its old pasted token rather than leaving a valid secret nobody reads. The issue cache is keyed on the **numeric** project id, not the path, with `projectPath` refreshed on every sync. Auth header is `PRIVATE-TOKEN` (what PATs are documented for, and what project/group access tokens also accept); pagination follows `x-next-page`.

**Consequences:** A self-hosted instance is a first-class source with no env var and no code change, and the common path is "pick the credential you already have, type the URL". Rotating that credential fixes cloning and issue import at once, because there is one secret rather than two copies drifting apart. The costs: deleting a credential silently breaks the servers borrowing it (`getGitLabAuth` says so by name rather than reporting a bare 401), and the credential's token is not scope-checked at link time — a clone-only token connects fine and fails on the first project listing. A project renamed or moved between groups keeps its cached issues, which is the point of the numeric key; a project whose id changes (a fresh fork) is a new project, which is correct. Read-only for now: closing an issue when its feature reaches `done` is the same deferred write-back spec 20 left open for ClickUp.

## D-67 — A GitLab epic is a dev phase, and its link to an issue is copied, not joined (2026-08-28)

**Context:** The GitLab importer shipped understanding `project → issues`, which is GitHub's shape and only half of GitLab's. Work there is organised `group → subgroup → epic → issue`: an epic is a *group*-level object with a title and a description that gathers issues from several projects at once. Probing the live instance this was built against settled what the shape really is: one group held well over a thousand epics (a third of them in descendant subgroups), several top-level groups used no epics at all, and an issue fetched from one group turned out to belong to an epic of an entirely unrelated group.

**Decision:** Three scopes in one dialog — project, group (subgroups included, GitLab's own default for `/groups/:id/issues`), and epic. An epic becomes a `DevPhase` named after it with its description as the phase goal, because an epic already *is* what a dev phase is; group and project scopes name the phase after themselves. The issue→epic link is **denormalized onto `GitLabIssue`** (`epicId` global, plus `epicIid`/`epicGroupId`/`epicTitle` for display) rather than a foreign key into `GitLabEpic`: the epic routinely lives in a group the user never synced, and a join would drop the reference exactly where it is most useful. Everything epic-keyed uses GitLab's **global** id, since `iid` is unique only within one group. Group cache reads match on the `projectPath` prefix with a trailing slash, which picks up every subgroup for free and keeps a sibling `platform-legacy` out. `/groups` is queried without `min_access_level` — it filters to *direct* memberships and cut the visible groups to a tenth, returning nothing for a group readable through inheritance.

**Consequences:** A team whose backlog spans six repos under one group imports in one pass instead of six, and an epic import arrives already shaped as a phase with a real goal. The costs: group sync stops at 1000 issues and has to say so in the toast rather than silently truncate; the epic picker reads the cache (fresh as of the last sync) while the project and group pickers are live, which is the sync-then-review rhythm the issue list already had but is an inconsistency worth naming; nested epics are cached but the picker is flat, so importing a parent does not pull its children's issues; and the epic scope needs Premium — on Free, `/groups/:id/epics` 403s and the picker simply stays empty. Transport failures are now retried twice (never on a certificate error or a refused connection, which cannot fix themselves): the network this was built on returned DNS REFUSED for roughly three lookups in five, and a paged sync makes ten or more requests, so one flaky resolution used to kill an entire import and report it as an unreachable instance.

## D-68 — Import from the URL you are looking at, and keep the board's columns (2026-08-28)

**Context:** The scope pickers (project, group, epic) cover how work is *organised*, not how it is *found*. People arrive with a URL — a group board filtered by a milestone — that already names the slice exactly, and asking them to translate it back into a scope plus a filter is asking them to re-derive what is on screen. The board also holds information no scope can express: which column each issue sits in. On the instance this was built against, one board's issues spread across eight columns and ten projects, and importing them as "open → backlog" would have thrown all of that away.

**Decision:** A paste box resolves any GitLab URL — board, epic, milestone-filtered issue list, project, or a bare path — and syncs it in one action. Parsing lives in `lib/gitlab-url.ts`, Prisma- and fetch-free, so the URL grammar is unit-tested without a GitLab; only what the instance owns goes over the wire (a board's name, milestone scope and columns; whether a bare `group/dashboard` is a subgroup or a project, since on a real instance it can be either). The resolved origin is checked against the selected server, so a URL from another instance is refused rather than importing nothing. Board reads — and only board reads — go through **GraphQL**: GitLab 18 models board columns as work-item statuses, and REST returns `label: null` for every list with no list type, so the columns are simply invisible there. Each issue's status is cached on `GitLabIssue.boardStatus` and mapped by `mapColumnToStatus`, the *same* function the GitHub Projects import uses rather than a GitLab twin; "Released" was added to its done branch, where it had been falling through to backlog. The mapping runs server-side and travels as `suggestedStatus`, so the dialog does not grow the duplicate copy the GitHub board dialog carries (D-51).

**Consequences:** Selecting what to import is a per-issue checkbox plus a row of chips — all, none, and one per board column with its chosen/total — since a board's worth of issues over eight columns is not a list anyone ticks by hand. That row exists because the first cut shipped with none of it reachable: the gate choosing between a picker prompt and the review tree ignored a resolved URL, so a pasted board rendered "Pick a project to load its issues." and the whole tree never appeared. The API had been driven end to end against the live instance; nobody had opened the dialog. The gate and the grouping now live in `lib/gitlab-import-review.ts` with tests, because logic that decides whether a list renders belongs where a test can reach it, not in a component this repo has no way to render in CI. **Consequences:** The board that prompted this imports as one phase named after its milestone, with every issue landing in todo/in_progress/in_review/done as it sat on the board — verified end to end against the live instance. A board is only "this owner's issues, narrowed to a milestone", so it needed no reader of its own: the cache scopes collapsed into one `IssueScope` union covering project id, group path prefix, exact project path and epic id, plus an optional milestone filter. Costs and limits: the review is a flat list, not columns rendered side by side, so the mapping is shown per row (source column next to target status) instead of being drawn; a board with no milestone imports its owner's whole issue set, since the columns filter the view rather than the query; GraphQL is a second API surface to keep working against future GitLab versions; and `mapColumnToStatus` is now load-bearing for two providers, so a change made for one has to be weighed for the other.

## D-69 — The browser moves to the app, because the ports are what cannot move (2026-09-12)

**Context:** A sandbox running a front end and a back end could not be tested by hand. Each process gets its own Cloudflare quick tunnel (`sandbox-process-manager.ts`), so the two arrive on unrelated random hostnames and the front's `API_URL` is wrong from the viewer's browser whatever it says — rewriting it per start only trades that for a value baked at build time and stale before it boots. The symptoms that usually get patched individually are all the same cause: CORS between two unrelated origins, cookies that are now cross-site, and dev servers rejecting a `Host` they do not know — which is already why the preview script pins `--http-host-header localhost:<port>`. The request named Browserbase as the experience to aim for, and it does not fit for the same reason: a browser in someone else's cloud resolves `localhost` against *their* container, relocating the identity problem rather than solving it.

**Decision:** Run the browser **inside the sandbox**, where `localhost:3000` and `localhost:8000` both exist and already agree, and reach it from the dashboard over an **SSH port-forward** — never a public tunnel. Chromium is not installed for this: `installAgentBrowser` already puts Playwright's build at `/usr/local/bin/google-chrome` for the agents' screenshots, so the bootstrap adds only Xvfb, x11vnc and websockify, and the same Chromium serves both the human (VNC) and programmatic drive (CDP). Every listener is loopback — `x11vnc -localhost`, websockify on `127.0.0.1`, `Xvfb -nolisten tcp`, and CDP pinned with `--remote-debugging-address=127.0.0.1`. The forward is a child of the web process (`ssh -N -L 127.0.0.1:…`, `ExitOnForwardFailure=yes`), so `reapForwards` settles rows on restart the way `recoverOrphanSandboxes` settles interrupted provisions. Navigation goes over CDP rather than VNC, which carries pixels and input and has no concept of a URL, and `isLocalTarget` restricts it to loopback: a session that could be pointed anywhere turns a browser holding the instance's localhost into a general-purpose fetcher for whatever reaches the route.

**Consequences:** Testing two services by hand needs no tunnel, no env rewriting and no CORS work — the app's own configuration is what gets exercised, which is the point. The costs are real and named: the VNC password is a per-session secret that must never reach a command line (`/proc/<pid>/cmdline` is world-readable), so it goes in through `x11vnc -storepasswd` inside a `set +x` window and the test asserts it appears exactly once; the session is off by default and forced off without `installAgentBrowser`, because a display serving no browser is memory spent on an instance nobody is looking at; a restart drops every forward, so a row saying `running` with nothing behind it would offer an iframe that can never connect; and per-process tunnels stay, since sharing a running app with someone not at this machine is a different need than testing it yourself. `shq` moved into the package's public exports — three callers now build remote commands with it, and one escaping implementation means a fix cannot land on only some of them.

## D-70 — The embedded browser, walked end to end on a container (2026-09-18)

**Context:** D-69 shipped the browser session — bootstrap, model, manager, routes and panel, with 27 tests — and every part of it had been exercised except the one that matters: nobody had opened the panel. Walking a local Docker sandbox from an empty database to a rendered app surfaced nine defects, of which exactly one was a missing feature; the rest were code that existed, typechecked, passed its tests and could never have worked. They are listed here because each one is a different way for a green suite to mean nothing.

**Decision:** Fix all nine, and add the local transport D-69 left open.

*Unreachable before the first pixel.* The panel imported `@novnc/novnc/core/rfb.js`; the package's `exports` is the **string** `"./core/rfb.js"`, so the bare specifier resolves and every subpath is refused — the whole project page 500'd, not just the browser. `installBrowserSession` had a column, a spec field and a template section but no UI and no field in the setup schema, so nothing could turn it on. "New sandbox" was gated on terraform plus a cloud token, which a container needs neither of, so a Docker-only machine never got to try. `SandboxConfig.provider` accepted only `civo | aws` although `launchSandbox` branches on `"local"`, and the drawer coerced a saved `"local"` back to `"civo"` — the two halves of one round trip, each making the other unobservable.

*Correct-looking code that cannot work.* The bootstrap runs as root and created the session directory `0700 root:root`; the session script runs as the agent user, so its first write failed and took the log with it — the panel reported "the virtual display did not start" and the evidence was the file that could not be created. The readiness probe was `curl -fs` against websockify, which answers a plain `GET` with **405**; `-f` fails on 4xx, so a healthy bridge was declared dead on every start. Navigation used CDP's `/json/new?url=<url>`, which Chrome 153 ignores while still answering 200 — one blank tab per click, success reported each time.

*The security one.* The password was written with `x11vnc -storepasswd - <file>`, read as "take it from stdin". x11vnc does not read stdin: it stores the literal `-` as the password. Every session on every sandbox authenticated against a dash while the UI handed out a per-session token that had never once worked. Confirmed by byte-comparing the stored file against `-storepasswd '-'`. The fix is `-passwdfile`, which exists precisely for this — it reads the plaintext from a file's first line *because* `-passwd` would expose it in `ps` — so the secret still never reaches a command line, and the token is now what actually authenticates.

*The transport.* A container has no sshd, so D-69's forward has nothing to attach to and `localUrl` stayed null: the panel showed a running session it could not display. `docker run` now publishes the bridge on an **ephemeral** host port (`-p 127.0.0.1::6080`) — ephemeral because a fixed 6080 collides the moment a second local sandbox runs — and `browserWsPort` reads it back with `docker port`. That forced one deliberate loosening: docker forwards a published port to the container's *own* interface, which a loopback-only listener never answers, so websockify binds `0.0.0.0` under an explicit `wsAllInterfaces` flag set only for `provider === "local"`. The privacy boundary moves from the bind address to docker's `127.0.0.1::` binding, which never leaves the host's loopback. VNC and CDP are untouched: VNC is reached *through* the bridge, and an open CDP port is remote code execution against every origin the browser can see.

**Consequences:** A local Docker sandbox now runs the demo's front end on `:3000`, which fetches its back end on `:8000`, rendered in the dashboard — the case D-69 was written for, finally executed. 297 sandbox and 1254 web tests pass, with new cases pinning each defect above: the directory's owner, a probe carrying no `-f`, `local` surviving a save and a reload, the stored password being the token rather than a dash, the CDP target being the query string rather than a named parameter, the port parser against IPv4/IPv6/absent bindings, and the widened bind being opt-in with VNC and CDP still loopback. The deeper cost is the one worth keeping in view: this feature was merged with tests that asserted the *shape* of its scripts — that a `-storepasswd` appeared, that a probe preceded a marker — and shapes are what kept passing while the behaviour was wrong end to end. Two of the nine (the `-` password, the `url=` parameter) are external-contract mistakes no unit test of a rendered string can catch, and they were found in ten minutes of running the thing. `apps/web/.env` also does not exist in a fresh checkout and the dev path never runs `prisma migrate deploy` (auto-migrate is gated on `NEXUX_MIGRATIONS_DIR`, which only the packaged app sets), so a clean clone starts against an empty database and every page 500s — worth its own fix, and left out of this one.

## D-71 — A bootstrap step records what it did, instead of being read back out of its own prose (2026-09-21)

**Context:** The bootstrap has always *logged* what it did and never *recorded* it. Only two things were ever fatal — the main repo's clone, and its missing mount; every apt install, the docker install, `docker compose up` for the stack services, every non-main clone and **every install and build for every repo** degraded to `|| echo "[nexux] WARN: …"`, and the completion marker was written anyway. The only structured consumer of that was `retrySandboxSetup`, which recovered the failed steps by running `/^\[nexux\] WARN: (?:clone|install|build) failed for (.+?)$/gm` over the setup log. A failed stack `up` matched nothing, so a sandbox whose database never came up reported a successful retry. Spec 24 piece 1.

**Decision:** Keep the policy, fix the reporting. Every step that mattered now runs through `nexus_step` / `nexus_step_run` (`packages/sandbox/src/bootstrap-report.ts`) and appends one JSON line to `/opt/nexus/bootstrap-report.jsonl`: step name, severity, exit code, duration, timestamp. The `echo` stays beside it — the log is still the live surface the UI tails, and a WARN vanishing from it would be a regression for anyone reading along.

**Why JSONL and not a document:** the writer is bash on a box that may be killed mid-run — a provider timeout, a reboot, the OOM killer. A half-written array is unparseable; a half-written JSONL file is merely shorter, and whatever ran is still readable. That is the case the format exists for, so the parser treats a truncated final line as expected rather than exceptional, and keeps it in `malformed` so a recorder bug stays visible.

**Why severity is an argument:** "fatal" and "warn" were already the policy, encoded as *which function the call site called*. Deriving it from the exit code would collapse the distinction — a failed main clone and a failed tailscale install both exit non-zero, and only one of them means the box is useless. Passing it makes the same policy readable by a machine.

**Three things the implementation forced, each a bug found by running the generated shell rather than matching its text:**

- `renderRepoSetup` is also run standalone by the retry action, where the bootstrap preamble is not in scope — so it re-emits the helpers, and declares a `nexus_bootstrap_fatal` fallback only `if ! declare -f`, so the bootstrap's own version (which writes the marker the host polls) is never replaced.
- `date +%s%3N` is GNU-only. BSD `date` does not expand `%N` and returns the seconds with a literal `3N` glued on — a string that is not a number, which every arithmetic use of it then fails on. `nexus_millis` falls back to whole seconds: coarse, not wrong.
- Timing variables are `local` inside the helper rather than assigned at the call site. The sites nest (a repo section runs inside the repo setup block), and a bare global would be overwritten by an inner step before the outer one read it — producing a *plausible* duration rather than an error.

**Two defects fixed in passing.** `parseBootstrapLog` derived `complete` from `/bootstrap finished/` over the tail, but the failing branch prints `bootstrap FAILED`, which does not match — so a bootstrap that had already failed read as still running and the log viewer polled forever, while the health strip (reading the markers) already knew. Completion now comes from the marker files, with `failed` as a separate field: *finished* and *succeeded* are two questions, and the old field answered neither reliably. The log is untrusted text anyway — a repo's own build output can print "bootstrap finished", and used to be believed. The marker query also needed `|| true`: a missing marker is the normal case mid-run, and `test -f` failing would otherwise become the exit status of the whole command, so `execRemote` would report a failed read and hide the log behind an error about a file that is absent on purpose.

## D-72 — The sandbox now starts the app before calling itself ready (2026-09-21)

**Context:** A sandbox has always been declared ready without ever starting the app it exists to run. `runCommand` reached `/opt/nexus/nexus.json` and the process plans, but no bootstrap section invoked it — so "provisioned successfully" meant "the tooling installed", and whether the project compiles, binds and serves was discovered by a human clicking Start, minutes later. The health strip reinforced it: five pills answering *is claude installed*, none answering *does the app respond*. Spec 24 piece 2.

**Decision:** Two changes, one per half of the lie.

**Healthchecks, derived from the image.** The bootstrap has always run `docker compose up -d --wait --wait-timeout 180`, which reads as "wait until they are ready". Without a `healthcheck` block it is not: compose waits for *running*, and for postgres that is true several seconds before it accepts a connection — the race a repo's install loses when it runs migrations. `healthcheckFor(image)` (`packages/harness/src/healthcheck.ts`) now supplies one for the families we recognize, and `depends_on` became long-form so a dependency with a healthcheck is waited *for* rather than merely started before.

Derived from the image rather than carried on the node, deliberately: a `StackNode` persists its image but not which catalog entry it came from, and a user may type `postgres:16-alpine` themselves. Matching the image means a hand-typed database gets the same guarantee as a catalog one. An unrecognized image gets **null**, which is a real answer — a generic port probe tells us no more than `--wait` already does, and a guessed probe can mark a healthy service unhealthy and block the whole `up`. `service_started` is used for those dependencies, since demanding health from something with no healthcheck hangs forever.

**The boot probe.** Each repo that declares both a run command and a port is now started, waited for, and **stopped again**, as a `boot:<repo>` step. A test, not a launch: leaving it running would make every provision also a deploy, and would race the user's own Start, which kills by its own recorded PID and knows nothing about this one. A repo without a port is skipped rather than probed loosely — "the process stayed alive for three seconds" is not evidence anything works, and reporting that as a pass would be the same lie in a new place.

**Three things the implementation forced:**

- **`set -m`, not `setsid`.** The kill has to reach the process *group*: `pnpm dev` spawns the real server as a child, so killing the recorded PID alone leaves the port held by an orphan and the user's later Start fails with EADDRINUSE on a box that had just passed its probe. `setsid` is util-linux and absent on macOS, where these helpers are unit-tested — a kill that is only correct on the platform the tests cannot exercise is a kill nothing verifies. Bash's own job control puts the job in its own group on every platform.
- **`curl -s`, not `curl -f`.** `-f` fails on 4xx, and an app whose `/` legitimately answers 401 or 404 is nonetheless up. The question is "does something serve HTTP here", not "is the root route happy" — the second is the app's business.
- **The failure carries a log tail**, JSON-escaped through python3 (`nexus_step_tail`). "Did not answer on port 3000" is not actionable on its own, and a build error routinely contains quotes, backslashes and newlines — any one of which, unescaped, produces a report line the parser drops.

**A false green worth recording.** The two tests that assert the app is stopped afterwards initially passed for the wrong reason: `setsid` was missing on macOS, so the server never started, and "the port is free" is trivially true of a server that never ran. Both now assert the app came up *before* asserting it went down. A test that cannot fail for the right reason is not covering anything.

## D-73 — Validation answers two questions, and says which is which (2026-09-21)

**Context:** Pieces 1 and 2 made a bootstrap record what it did and prove the app boots. Nothing surfaced either: the report sat on the sandbox, and the only pre-flight a definition ever got was `generateCompose`'s four structural warnings — which only ever described the YAML it was about to emit. Spec 24 piece 4.

**Decision:** A **Validate** action, between Preview compose and Up, and two read-only MCP tools. Its answer has two halves that are never merged:

- **static** — definition checks (`lib/stack/validate.ts`): dependency cycles *naming the nodes in them*, port collisions, services with no image, docker repos with nothing to build, placeholder env values, and dependencies nothing can probe. Pure: no filesystem, no docker, no network.
- **observed** — the `boot:*` / `install:*` / `stack:up` steps the project's most recent sandbox actually recorded, read back over SSH.

**Why they stay apart.** Merging them into one verdict forces a choice between two lies: claiming a definition boots because it passed a lint, or calling it unvalidated because nobody has provisioned it yet. The static half cannot prove anything runs; the observed half is the only evidence that does, and it may be absent, stale or unreachable. The UI says which it has, and `booted` is **null** — not false — when no app declared a port, because "nothing was probed" and "the app failed to start" are different answers.

**Most recent sandbox, not a healthy one.** A sandbox that failed to provision is the most informative evidence available; preferring an older green one would report a stack as working *because* its latest attempt broke.

**What validation does not do.** It does not resolve a port collision for you — picking one changes the URL you expect, and which node should move depends on which is "the" app. It does not gate the wizard. And it does not provision: both MCP tools are `projects:read`, because the static half is pure and the observed half reads a report off a machine that already exists. A token that can look at a project can ask whether its stack holds together.

**Verified against a real sandbox**, not only in tests: a three-day-old box, provisioned before the recorder existed, answered "That sandbox recorded no steps — it predates step reporting", which is the fallback path behaving exactly as designed rather than an error.

**Note on scope.** Piece 3 (the fast dry-run sandbox) is not built, so `validate` reports on the last *real* provision rather than running one on demand. That is the honest version of the feature at this stage — it never claims to have run something it did not.

## D-74 — A dry run starts where the validation does (2026-09-23)

**Context:** Pieces 1, 2 and 4 made a bootstrap record its steps, prove the app boots, and surface both. They did not make asking cheap. A local sandbox is byte-identical to a cloud one — `local.ts` calls the same `renderCloudInit`, only in container mode — so every run paid apt update, build-essential, the NodeSource curl|bash, `get.docker.com`, a global `npm i -g` for the agent CLIs, the gh keyring, a glab `.deb` and, longest of all, `playwright install --with-deps chromium`, into a bare `ubuntu:22.04` with no layer cache. With spec 25's repair loop running up to three rounds, that is an hour to answer one question. Spec 24 piece 3.

**Decision:** Two levers, both already latent in the code.

**A prebuilt base image**, `nexux/sandbox-base:v<N>`, holding the tooling half of the bootstrap. It is generated from `base-image.ts` rather than hand-written, and a test asserts the same install markers appear in both it and `renderCloudInit` — a parallel definition is one that drifts, and the drift here produces the worst possible failure: a dry run passing against tooling the real sandbox does not have.

**A trimmed spec** (`dryRunSpec`) that drops the agent CLIs, Chromium, the tunnel and the tailnet. Each is either tooling a validation does not use or reachability it does not need — a dry run works off bind-mounted checkouts, so there is nothing behind a tailnet to clone. `installDocker` is deliberately *not* dropped: the caller may have forced it on because the canvas has compose services, and a dry run that quietly removed Docker would report a stack as broken for a reason the real provision would not have.

**Measured, not asserted.** With a real repo (pnpm install, a build, an express server on :3000): **52s → 23s**, all three steps recorded green. The image itself builds in ~45s and is cached after that.

**Never builds inline.** `resolveBaseImage` falls back to `ubuntu:22.04` when the image is absent or its version label is stale, and the bootstrap then installs what it needs exactly as before. A launch that quietly spent five minutes building would be the same twenty-minute surprise this piece exists to remove, with a different cause — so building is an explicit action the caller pays for knowingly.

**The version is a label, not a tag.** `baseImageIsCurrent` reads `org.nexux.base-version` off the image, because a tag can be retagged and an image claiming v1 while holding v0's tooling is precisely the silent wrong answer the whole spec is about.

**One thing the first build got wrong**, caught by running the image rather than trusting it: `corepack prepare --activate` writes a *shim*, not the binary — the real pnpm downloads on first use ("Downloading the pnpm 12.6.0 binary for linux-arm64"). The image had baked a package manager that still needed the network before it could install anything. Invoking `pnpm --version` and `yarn --version` in the same layer pulls the binaries in; v2 answers instantly.

**End to end on a deliberately broken app**, to check the loop reports what a repair agent would need: 24 seconds from launch to `install=0 build=0 boot=1`, with the boot step carrying `Error: Cannot find module '@acme/does-not-exist'` in its tail. That is the actionable failure spec 25's repair loop reads.

## D-75 — A repository is not a node, in the schema as well as the model (2026-09-23)

**Context:** Detection has always been good and always been unused: `detectRepo` finds the Dockerfile, the compose file, the package manager, the scripts, the env keys and the ports, and parses each Makefile target's recipe so a `make dev` that is secretly `docker compose up -d postgres` is recorded as such. All of it fired only when a human dragged a repo onto the canvas, and prefilled exactly one node. Nothing turned it into a graph, so every project started blank. Spec 25 piece 1.

**Decision:** Discovery in two passes. `findRunnableUnits` reads the workspace declaration (`pnpm-workspace.yaml`, `workspaces` in package.json) and expands it into directories; `detectRepo` then scans each one, unchanged — it already took an arbitrary path. `seedStack` turns the results into nodes, inferred services and edges.

Two repos with one app each, and one monorepo with two apps, now produce **the same graph**. Only discovery differs, which is the point: the stack describes what boots, and a git is how the code arrived.

**The schema said otherwise.** `StackNode.repositoryId` was `@unique` — "one repo, one node", enforced by the database. The seed hit it on the first real monorepo. Nothing depended on the uniqueness (every read is by `id`; the one query filtering on the column already used `findMany`), so the migration replaces the unique index with a plain one and the `Repository` back-relation becomes a list. Worth recording because the spec treated this as a matter of inference and it was also a constraint.

**What the inference will and will not claim:**

- **Scheme first, name second.** `DATABASE_URL=postgres://…` names its engine and is conclusive. `POSTGRES_HOST` alone is suggestive: the node is still created, flagged low confidence with the evidence attached. Silence would leave the blank canvas this piece removes; an unlabelled guess would be worse.
- **One service per project, not per unit.** Three units naming a database want one postgres between them. Three containers racing for 5432 is a boot failure nobody asked for.
- **A repo that ships its own compose file suppresses inference entirely** — it has declared its services, and duplicating them starts a second postgres fighting the first.
- **Unit-to-unit edges are never inferred.** A front end's `API_URL` pointing at a back end's port is suggestive, not conclusive, and a wrong edge changes boot order in a way that is hard to debug. Two apps in one git are no more related than two gits; treating co-location as evidence is exactly the wrong inference.
- **A library is not a node.** A unit earns one only if it has something to run — a dev/start script, a Dockerfile, or a flagged make target. A workspace of nine libraries and two apps is two nodes.
- **Port collisions are flagged, not resolved.** Two apps defaulting to 3000 is common; picking one for the user changes the URL they expect.

**Seeding refuses a non-empty canvas.** A merge cannot tell a deliberate edit from a stale one, and silently reverting a hand-written fix is the worst outcome available. Re-seeding is explicit, and then it replaces.

**One bug only the real monorepo revealed.** A workspace member does not declare its own package manager — the root does, and detection scans each unit in isolation. The first real seed gave every app in a pnpm monorepo `npm install`, which at best ignores the workspace and at worst writes a package-lock.json beside pnpm-lock.yaml. Members now inherit the root's manager, unless they detected their own (a lockfile of their own is better information than the root's).

**Walked end to end** on a monorepo with two apps and a library: two run nodes, postgres and redis inferred from the API's `.env.example` with the connection strings as evidence, edges only from the unit that named them, the library reported as a library — and `validate` then answered clean on the result.

## D-76 — The repair loop's rules live in the applier, not the prompt (2026-09-23)

**Context:** Spec 24 made a failure readable — a `boot:api` step carrying `Cannot find module '@/generated/prisma'` in its tail. A human reads that and knows the install is missing a codegen step; the system did not, so the developer was still the one closing the loop. Spec 25 piece 2.

**Decision:** Validate → read the failures → the stack assistant proposes patches → apply → re-validate, up to three rounds. The agent is the existing assistant with a different prompt and caller: its suggestion format is already an applied patch with a reason, and its tools are already the right three. A second agent would be a second definition of what a stack patch is.

**The split that matters.** A prompt is a *request*. "Never remove a run command" in an instruction block is a sentence a model may ignore, misread, or reason its way out of when a failure is stubborn. So every rule the loop must not break lives in `lib/stack/repair.ts`, which is the only thing that writes:

- **Never weaken the check.** Blanking a `localCommand` or a `ports` array makes validation pass by *not running* — the node stops being started, or the boot probe is skipped and "the app failed" becomes "nothing was probed". Refused, with the field named. Changing a command to a different one is fine; the rule is about removal.
- **Never touch a node the user wrote.** This needed a fact the database did not record and that cannot be recovered afterwards, so `StackNode.seededBy` is new, defaulting to `"user"` — every node that exists today was put there by a person, and the safe direction for a rule protecting hand edits is to assume the edit was one. The seed writes `"detect"`, a repair writes `"agent"`, and a later round may revise its own work.
- **Never create a node.** Adding a service the project never asked for is a guess with a container attached. Inference belongs to the seed, where it is driven by the repos' own evidence.
- **Never patch a node that does not exist** — the ordinary failure of a model reading a truncated tool result.

Good and bad suggestions in one reply are separated rather than rejected together: the fix lands and the weakening does not.

**Three rounds, and a round that proposes nothing stops immediately.** Each round costs a validation — a container, and real money on a cloud provider. Re-validating after changing nothing would ask the same question and get the same answer, so the loop returns rather than spending it.

**No separate "propose" mode.** `POST /stack/validate` already is one: it reports what is wrong and changes nothing. A second endpoint that ran the agent without applying would spend a validation to produce advice the user cannot act on without re-running everything anyway.

**Every round records what changed and why**, plus what was refused. The safety story is that nothing happens silently — an agent that rewrote three nodes over two rounds has to be reviewable without reading the database.

**Verified end to end against a real port collision**, where it behaved correctly for a reason worth recording: the run stopped at the agent (no OpenAI key configured) and the canvas was untouched — and both nodes were marked `user`, so even a working agent's patches would have been refused. The rule held without the model's cooperation, which is the whole point of putting it in the applier.

## D-77 — Host agents run on whichever LLM you actually have a key for (2026-09-23)

**Context:** Nexus has been multi-provider everywhere except the one place it mattered most. Sandboxes fan six LLM credentials out as env vars (`LLM_CREDENTIAL_ENV`), the brain picker offers Claude or OpenCode — and every agent running *on the host* (the stack assistant, the repair loop, the roadmap generator, the definer, the skill recommender) hardcoded `modelProvider: "openai"` across seven call sites and read a single `openai_api_key` setting. A user holding an Anthropic key and no OpenAI one was told to "add it in Settings", which reads as a missing configuration and was really a default nobody had parameterised.

**The SDK was never the constraint.** `@ideascol/agents-generator-sdk` takes provider, model and key per `defineAgent` call and ships **75 providers** — including every one Nexus already stores. Checked rather than assumed, which also caught a default model name (`zai/glm-4-plus`) that does not exist; the real list has `zai/glm-4.5`.

**Decision:** `resolveHostModel` reads the same `CloudCredential` rows the rest of the product does, mapping our provider names to the SDK's (`anthropic-key` → `anthropic`, `xai-llm` → `xai`, `google` → `gemini`). Precedence: the credential the user chose → any usable saved one, oldest first → the legacy `openai_api_key` setting.

**Three judgements in that ordering:**

- **The legacy setting stays.** Every install that exists today is configured that way, and breaking them to introduce a choice is a poor trade.
- **A chosen credential that has since been deleted, or had its key emptied, falls through rather than failing.** The user's intent was "use a model"; serving that with a different key beats doing nothing.
- **`claude` is deliberately not in the map.** It holds an OAuth token for the Claude Code CLI, which is not an API key this SDK can send — a project with only that is still unconfigured, and pretending otherwise would fail at the API with a confusing error.

The error message now names every provider that would work, instead of sending people after an OpenAI key they may have had no reason to own. `GET/PUT /api/settings/host-model` exposes the choice, and lists a credential with an empty key as *unusable* rather than hiding it — "I added that key" and "that key is empty" are different problems, and a hidden row makes the second look like the first.

Found while the repair loop (D-76) stopped on a missing key and the honest answer to "why can't I pick another token?" turned out to be: you could have, nobody wired it.

## D-78 — A lock describes a boot; it does not pin one (2026-09-23)

"Reproducible" had no definition in this codebase, and the largest source of
drift was structural and invisible: a local sandbox bind-mounts repo folders
([local.ts:231](../packages/sandbox/src/local.ts:231)) while a cloud sandbox
clones by URL. A stack validated locally was validated against someone's working
tree — uncommitted files included — and nothing anywhere said so.

`StackLock` records what a green validation passed against: commits, dirty
flags, lockfile hashes, image digests, tooling versions, and how the code
arrived. Spec 25 piece 3.

- **It is not a pin.** Nothing reads a lock back to force a digest. Pinning an
  image the user did not pin has real consequences — a postgres that never gets
  a security patch — and that choice is theirs. The lock *describes*; if pinning
  is wanted later, this is the data to generate it from.
- **A lock needs proof of a boot, not a passing lint.** It is written only when
  `observed.booted === true` and no step failed. Spec 24 spent its fourth piece
  keeping "the definition is well-formed" apart from "it runs"; locking on a
  static pass would have collapsed that distinction from the other side, by
  stamping "booted against these commits" on a stack nobody ever ran.
- **`source` comes from the repos, not the provider.** `local.ts` mounts only
  repos with no clone URL, so a local sandbox whose repos all have remotes
  clones exactly like a cloud one. Reading it off the provider would have
  labelled those runs `mount` and told the user their green was weaker than it
  was. Mixed reports `mount`: if any repo was mounted, the run saw a working
  tree, which is the weaker of the two claims.
- **Digests come from the local daemon only.** Resolving a tag against a
  registry turns a validation into something that fails when the network does,
  for a field that is a nice-to-have. An unpulled image records `null`, read as
  "we do not know" rather than "it has no digest" — and the diff treats
  null-to-null as no change rather than as drift.
- **One row per green run, not one per project.** The whole point is to diff
  this run against the last one, and a single overwritten row can only ever
  describe the present.

Committing the lock into the user's repo was the more honest framing of what it
is, and was rejected for the same reason: one file in a working tree describes
now, and the question a lock answers — "it was green on Tuesday and red today"
— is a question about history. It would also have made Nexux the only tool here
that writes files into someone else's git.

Collection is best-effort throughout. A missing git, a stopped docker, a path
that is not a checkout: each yields a null field rather than an exception, and
the lock write is wrapped so that failing to record one never changes the
verdict of the validation that earned it. A lock with a null digest is worth
strictly more than no lock.
